## Standards：1 项 P1

### S1：Planning claim 恢复可绕过来源复查

基线 `planning_execution.py:696–700` 持久 `submit_claimed / submission_started=False`，`730–741` 只在 started 为 true 时阻止重投。两事务之间中断后，用没有 admission/output authority 的新实例调用公开 `submit()`，实际输出为 `submitted`，Run 新增 1 个 Plan。

违反 [#110 原 AC](worker-dispatch-20260907/issue-110.md) 的精确恢复、来源失效拒绝及无生产 authority 时 fail closed；[控制器说明](../implementation/planning-execution-controller.md) 只允许已有 Run receipt 的恢复不要求 live authority。

修复：首次提交权限定于本次真正写入 claim 的调用，已有 claim 只读查询原 receipt，缺失时返回观察性的 `submission_unknown`，保留 durable claim，避免恢复者阻断仍存活的首次调用。保留正常提交、已有 receipt 的丢回复恢复、取消和并发唯一 Plan。原修复作者提交 `a94fdd1326b8123f1ac89b862222a5bbb4a400bc`、机械集成 `064de2d94797b659f9ebe85f011a37ffa1120322`；后续修正见下方组合复核，最终以当前 PR head 为准。

## Spec：1 项 P1

### P1：Reviewer 输入遗漏批准任务的验收

基线 `reviewer_input.py:98/122/204` 忽略 `_approved_task` 返回值，仅将 `Run.requirement` 纳入输入。Run 验收与 Worker/Reviewer 的 `PlanTask.acceptance` 独立，Worker 已读取完整任务，但 Reviewer 看不到任务特有约束。反例在 Worker task 增加“不把 API token 输出到 stdout”，公开 compiler 的 bytes 中不存在该条件；Reviewer task 的独有 AC 同样遗漏。

违反 [#114 原 AC](worker-dispatch-20260907/issue-114.md) 的“原批准需求/验收”，影响未来业务 Review 的完整性。当前还没有生产 Reviewer consumer，不能声称已造成真实错误交付。

修复：从真实当前批准 plan/operation/source 读取两任务的 ID/revision/role/paths/acceptance 和必要计划/批准身份，校验绑定后编入 `karajan.reviewer-input.v2`。完整 bytes/digest 随格式改变，原 Candidate 身份不改，旧 v1 不是新输入证据。真实批准 Run/operation/CAS 回归补充两任务验收、旧计划/任务/批准摘要拒绝。作者提交 `b30ed6a99e8e04a83994187b54e218c551163417`，机械集成 `cb206ae1053be08d53b1fc4aebecaf085ef09141`；当前候选仍需最终双审和 CI。
