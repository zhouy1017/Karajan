## 默认代码模板首演：Commander Workbench

按以下顺序完成一条可复核的用户路径：

1. **P1 开仓库会话。** 用户从认证工作台打开受管仓库，选择 Commander 模型和来源后进入 Commander Hub。持续会话与任务缩略卡片是主工作面，Tasks / Agents 列表和抽屉提供展开详情；返回 Hub 保留状态。首屏不要求填写资格、规则或预算表单。
2. **P2 显式分工。** Commander 持续对话并只读可信仓库和需求输入，提出初始任务图。用户可以编辑任务角色、指定模型来源、依赖、写权限和检查要求；服务端生成不可变版本，用户批准正在查看的同一版本。r8 另外明确调度角色与 SchedulerGrant，范围内后续拆分/绑定/派发自动提交运行图修订，不逐任务重复批准。严格指定单一 Profile 或来源不能被静默替换；只有用户明确启用并批准的替代集合，才允许在范围内自动创建新 Attempt。资格、能力和额度不足时显示具体状态：合法有限保守模式可以准入，超出硬 gate 则阻塞并等待决定。
3. **P3 最小并行整合。** 原票以两个无依赖任务、较低成本模型真实并行编码作为最小验收样本；每个任务有独立 workspace、Attempt、授权、资源和消费记录。两任务不是产品默认数量或上限，r8 完整运行图由获授权角色按需求决定，实际容量不足则排队保留。完成后按固定顺序组合候选并重新验证，冲突、越界、失败、取消和 unknown 均保留可查询事实。
4. **P4 checks 独立 review 交付。** 对组合候选运行必需 checks；独立 Reviewer 从新上下文读取同一 Candidate 和证据，工作台显示 checks、Review、diff、当前 head、PR 和限制。失败或不确定阻止交付；响应丢失先查询同一对象，不能重复创建 PR 或覆盖外部 head。

P1–P4 是实现顺序，不会自动关闭父票或改变原验收门。P3 的并行实现切片可以在 #17 的完整交付条件满足前独立验收；#17 原有对 #14/#15 的最终依赖仍是其完整验收 gate。P4 的真实来源、GitHub 交付和 v1 出口依旧分别由 #13/#14/#95 及其子票承担。

2026-09-09 r2 明确 P1–P4 是开发顺序，而非要求用户逐页跳转的操作向导。Commander 在 Hub 提出拆分和初步分配，用户在 Hub 调整确认后分发并留在主会话。P3 的进展/阻塞和 P4 的成果、checks、独立 Review、PR 状态都由缩略卡片与 Commander 汇报回归 Hub；具体证据和更多操作从详情展开。UX-AC11 跨四票承接，各票只验收自身阶段，原依赖与真实证据门保持不变。

r3 将实时反馈图标与最近事件时间、快捷新对话/新任务入口纳入 P1，并由 P2–P4 接入真实计划和运行反馈。新建不覆盖旧会话，不绕过批准；反馈过期或连接中断显示待核对，不以持续动画冒充运行健康。

r4 将“项目 → Commander 会话”的侧栏层级纳入 P1/UX-AC14。切换项目恢复各自草稿、任务和反馈状态，快捷新建绑定目标项目；P2 的计划/批准和 P3/P4 的异步执行证据沿同一项目/会话身份校验，不因导航串用或扩大授权。

## 模型、调度与权限边界

以下模型分工只约束开发本仓库的 Agent，不是产品内可自定义角色的硬编码限制。

- `gpt-5.6-luna`：简单 UI、DTO、边界明确的适配和定位清楚的修复。
- `gpt-5.6-terra`：生命周期、权限、预算、隔离和跨模块接线。
- `gpt-6-astra`：协调、关键判断和独立 Standards / Spec 审查；不编写产品代码、测试或 CI。审查发现阻塞时回派原适合的 worker。

获授权角色负责业务拆分、绑定、依赖和派发决策，可信服务校验 SchedulerGrant/SchedulingDecision 并提交 TaskGraphRevision，负责 admission、幂等、状态推进、恢复和证据收据；纯状态更新不轮询主模型。动态扩展集合封口且必需输入齐备后才汇合，不能通过删图抹掉已承诺义务。用户固定的绑定及允许选择/调整的范围保留在批准 envelope 中；严格单一 Profile 不得被替代，已由用户启用并批准的替代集合可按原范围自动创建新 Attempt，且不重复批准。能力额度、认证、计量、隔离和用户明确资源政策是硬 gate；合法有限的保守 unknown 模式只有在当前策略明确允许时才能准入。任何真实容量限制只约束可执行时机，不自动成为任务图或 Agent 数量上限。

本轮不扩大既有消费权限。Go、ChatGPT/Codex 和 Claude 的已有授权事实按各自资格记录使用；现金 API、订阅外余额和现金后备继续暂停。文档、候选创建、CI、独立 review 和 PR 页面存在不等于真实能力通过；合入、发布和关票仍按 [Issue 跟踪流程](../agents/issue-tracker.md) 的原 AC、候选 commit 和 C/U/P/S/G 证据核对。

## 每批完成条件

r8 创作/部署切片必须用真实持久文件、同版图表/确认、目标调度器加载回执和重新打开的生效状态验收。完整体验还需从部署版本创建 Run，并由获授权角色实际提交扩图/派发、按配置执行；加载成功、实际模型调用和产物完成分别取得证据。只通过 parser、导出 YAML 或显示“已部署”按钮状态不能升级为 WD-AC 通过。FR26/27、UX-AC23/24 与 RS-AC 另行证明范围内自动生效、越权/过期拒绝、无内置数量上限、动态集合封口、容量不足排队及恢复幂等，不能用原两任务样本代替。

每批先说明新产生的可观察行为，再选择最短可验证链。只派输入、输出、修改范围、证据层级和依赖清楚的任务；调度运行、模型自述或本地 fixture 不能单独算完成。每项原 AC 保留 `not_run / passed / failed / unsupported`，旧候选的通过不能自动升级新候选。

原 P1 只有在真实认证页面进入会话、持久 Task/Agent 事实可读回并完成 U/C 证据时才算首个 UI 切片完成；原 P2 只有在显式分工、同版批准和旧版本拒绝可复核时完成；原 P3 只有在两个已授权较低级别模型的独立 Attempt 实际并行、组合候选重新验证且取得 S 证据时完成；原 P4 只有在 checks、独立 Review、diff/head/PR 和限制均绑定当前候选并取得相应 C/U/P/S/G 证据时完成。两任务仅保留其最小验收责任，不成为当前产品人数上限；r8 调度和真实来源资格、完整 v1 仍需各自出口。

## 保留范围与未覆盖事实

完整 PRD 原 AC、架构设计、M0–M4/DG 历史路线、examples 证据、GitHub Issue 状态和失败记录继续有效。多来源覆盖、完整资源/预算产品、自动换源、恢复/升级/保留、任意第三方通道、真实连续运行和完整 v1 出口仍是后续范围。Go 固定场景和已合入离线原语的证据只覆盖明确子集；未取得真实服务、隔离、调度或远端交付证据的能力保持 `not_run` 或原记录的 `failed / unsupported`。
