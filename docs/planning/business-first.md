# 当前业务顺序

这是当前唯一的开发执行入口。当前产品闭环任务是 [#153 工作台业务闭环](https://github.com/zhouy1017/Karajan/issues/153)，本地固定输入、缺口和原 AC 见 [#153 业务简报](business-first-issue.md)；其原生父票为 [#12](https://github.com/zhouy1017/Karajan/issues/12)。原 PRD、Issue 正文、架构约束和验收清单仍是范围基线；未提供的外部事实保持阻塞。

## 一条可演示主线

1. **第一演示：**用户在工作台提交一个小需求；真实 Commander 只读目标仓库生成计划；页面展示计划、范围、权限和资源影响；用户精确批准这个版本。演示输入、期望行为和当前缺口以 [#153 业务简报](business-first-issue.md) 为准。页面已有需求保存、计划展示和精确批准组件；当前断点是后端尚未接通 Planning controller/admission/业务 transport。
2. **同一需求交付：**按批准版本派一个 Worker Candidate，运行必要 checks；独立 Reviewer 从新上下文读取同一 Candidate 和证据；交付同一真实 PR，并在页面显示 Candidate、checks、review、head 和限制。
3. **之后扩展：**再做并行、多来源、完整资源/预算、换源、恢复和维护。它们不能改变第一条主线的行为约束，也不能把未验收能力写成已完成。

当前只推进这一条业务主线，最多保留一个独立、直接阻塞它的修复。复用 `#112`、`#113`、`#142`、`#146`、`#147`、`#151` 及已有候选；`#147` 只提供 Commander 资格前置，不能替代 #153 所需的业务 transport。先闭合工作台到持久 Planning 的入口，再完成同一需求的真实生成；Worker Candidate→checks→Reviewer→PR 排在首个计划演示之后。候选完成后再排 Reviewer `#116`、`#143`、`#107`、`#149`，按当前候选可消费的资格推进，不等待全局资格全部完成。候选和 Reviewer 的原 AC、依赖与证据仍按 [Issue 跟踪流程](../agents/issue-tracker.md) 逐项核对。

## 模型和工作边界

- `gpt-5.6-luna` 默认 medium：UI、DTO、边界明确的适配和定位清楚的修复。
- `gpt-5.6-terra` medium/high：生命周期、权限、预算、隔离和跨模块问题。
- 只有已有具体失败，或复杂度已清楚升级时，才提高档位或改派；一次失败后保留反例和证据，不无限重试。
- `gpt-6-astra` 负责协调、关键判断和独立审查；不写产品代码、测试或 CI。独立审查保留 Standards/Spec 结论，阻塞修复回派合适 Worker。

## 每批执行和完成条件

授权事实沿用既有记录：Go、ChatGPT/Codex 官方订阅和 Claude 官方订阅的真实测试已获授权；现金 API、订阅外余额和现金后备仍暂停。每次真实执行仍核对具体来源和原有界额度，资格未通过不启用相应产品角色。文档不新增合并或消费权限；开发 PR 合并沿用当前会话授权，产品计划仍由用户批准精确版本。

每批先向用户报告新能做什么，再选择最短可验证链；只测必要边界，同时保留必需 CI、独立审查和已有授权。先读 [Issue 跟踪流程](../agents/issue-tracker.md)，恢复当前候选、PR、checks、依赖和具体缺口；只派有明确输入、可观察结果和独占范围的任务。每批按其既定原范围和适用的 C/U/P/S/G 证据验收；首演只有在 #153 的真实计划生成与精确批准可复核时才完成，最终产品交付阶段才要求同一真实 PR 的完整证据。派发、CI 运行中或模型自述不算完成。
