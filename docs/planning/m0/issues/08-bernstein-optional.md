# M0-X｜可选：评估 Bernstein 能否服从 Karajan 执行契约

## 用户价值

只在底座确实减少实现成本且不夺走调度权时复用它，避免把跨来源路由、预算和交付状态分散在两个系统。

## 范围与演示

固定一个可获取版本，用假适配器与本地任务演示外部调度、生命周期回执和候选回传。以下 B1–B8 完整列出已确认架构中的 Bernstein 采用门，沿用其原编号与含义，不做大范围 fork：

1. B1 固定版本：包/源码/配置可追溯，外部 Attempt 身份、输入和固定 Profile 等必需启动字段实际被接受。
2. B2 执行前拒绝：注入 admission 拒绝或异常时，执行及模型请求计数符合声明的阻断范围；明确覆盖 Attempt 还是每次模型请求，不能将前者推断为后者。
3. B3 配置不漂移：模拟重试、续接和配额错误，模型、执行器、认证或计费配置不静默改变。
4. B4 内部工作受控：delegation/fallback/continuation 能禁用或全部受授权及消费控制；不可观察的部分标为 unknown，不能据此宣布所需控制通过。
5. B5 启动可核对：模拟已启动但回执丢失，通过唯一执行身份定位原执行；状态未知时不重复 spawn。
6. B6 恢复与取消：start/inspect/cancel 区分 running/exited/unknown，进程树和 session 可核对；迟到结果不恢复已取消任务。
7. B7 无竞争控制：不启用自治 DAG、选路、业务重试或交付循环；只返回候选及执行事实供 Karajan 决定下一步。
8. B8 无交付权限：用假凭据和本地端点验证执行器/项目工具无法借用 Git 凭据或交付端点，不访问真实外部写入目标。

## 验收标准

- [ ] 每项能力都有版本、输入、观测和证据；未获得运行版本或未执行用例时填 not_run。
- [ ] 给出采用、暂缓或不采用结论及最小理由；不能仅引用 README 宣布契约通过。
- [ ] 若需大范围 fork 或存在第二个业务调度源，明确不纳入当前路径，保留直接适配器方案。
- [ ] 记录满足契约所需的最小扩展接口和版本升级资格成本；维护成本作为采用决定的依据，不替代任何 B1–B8 能力验收。
- [ ] 研究工作可因有证据的 failed/unsupported 结论完成；不能因此把不合格能力标成 passed。
