# 角色主导的任务拆分与调度

修订：2026-09-14 r8。状态：**按用户要求接受本设计方向，待实现与验收。** 对应 FR26/FR27、UX-AC23/24。Workflow 中获用户授权的调度器、Commander 或其他角色按实际任务决定拆分、分工、优先级和派发；Karajan 不内置前后端划分，也不内置 2、4 或其他产品级 Agent 人数上限。本文不声称无限吞吐或当前已经支持真实动态并行。

本契约承接 [可配置 Workflow](09-configurable-workflows.md)、[r7 对话与部署](10-conversational-workflow-deployment.md)、[控制状态](01-control-and-state.md) 和 [资源准入](02-routing-and-quota.md)。它修订“全部任务必须预先列出并逐版人工批准”和“默认两个 writer”的产品限制；原固定规模示例仍可作为测试场景，既有 [网关边界](08-provider-gateway.md)、隔离及 PR 证据门继续有效。决定见 [ADR 0008](../adr/0008-role-directed-scheduling.md)。

## 1. 判断属于角色，提交与执行属于可信引擎

用户在 Workflow 中指定承担计划/调度的角色节点，并授予其具体工作范围。该角色可以读取获准需求和执行事实，发现工作、动态新增或细化子任务、选择获准职责与模型来源、调整依赖和优先级、决定哪些工作现在派发或暂缓。它可以决定一次任务需要 1、3、7 或其他数量的执行者，不要求 Workflow 作者先枚举这些子任务。

角色产出的是可直接生效的结构化调度命令，不限于供用户逐条点头的建议。命令在当前授权内通过校验后自动提交并推进；无需每个子任务或每次范围内调度再次人工批准。角色未获相应权限、命令无法证明处于现有范围或确需扩权时，才形成待决定的具体变更。

可信引擎负责校验身份、版本、授权、输入输出契约、能力、依赖、资源与产物门，持久化命令和图修订，按已接受决定执行实际准入/派发。它不另写一个隐藏的业务拆分器，也不把角色决定改成固定的前端/后端两任务模板。角色不能直接写数据库、启动未登记进程或取得 OS、网关管理及 PR 凭据；由受控 runtime 以绑定 ExecutionRef 的窄命令接口提交结果，模型不能自报身份取得权限。

“唯一协调器”继续表示唯一可信状态与副作用提交边界，不表示产品永远只有一个可以判断分工的模型角色。Workflow 可以授权多个调度角色管理不同范围；重叠范围的决定由版本比较和明确归属解决，不靠角色名或最后写入者抢占。

## 2. 明确且可委派的调度授权

`SchedulerGrant` 是用户批准范围内的权限记录，与可编辑的 RoleDefinition 分开。它绑定实际角色实例/执行身份，不能仅写 `role_name: Commander` 就获得能力。

| 字段 | 必需语义 |
|---|---|
| `grant_id/revision`, `issuer_ref`, `subject_ref` | 用户授权或有效父 grant、被授权角色实例/ExecutionRef；身份由可信控制层绑定 |
| `run_id`, `scope_ref` | 指定 Run、父任务或子图及其输入/目标边界；不能跨项目或借另一 Run 的授权 |
| `allowed_actions` | 明确允许 expand/refine、绑定角色/Profile、修改尚未执行依赖、设置优先级、请求派发/暂缓、关闭扩展集合等操作 |
| `work_contract` | 可读取材料、工作目标、允许路径/工具/数据去向、产物类型、风险下限与必须保留的验收义务 |
| `role/profile_refs` | 可绑定的固定角色/执行种类版本与已批准来源集合；变更角色名称不增加集合 |
| `resource_policy_refs` | 获批预算、来源与宿主资源政策、累计调用/时间/返工限制；只有用户明确设置时才包含 Agent/并发数政策 |
| `delegation_policy` | 是否可再委派、可委派动作/范围、明确的授权链深度或等效可验证终止边界；默认没有隐含转授权 |
| `validity/revocation` | 当前 grant revision、撤销状态、有效期或结束条件；终止后的迟到命令不能产生新工作 |

子 grant 由可信服务从父 grant 派生，权限、输入范围、角色来源和资源只能取子集；不能再授予父 grant 不具备的能力。预算与返工计数沿父链累计，不因新增角色、任务、grant 或图 revision 重置。授权链有界与子任务数量是不同约束，不能把委派深度偷换成全局 Agent 上限。

用户授予的是可验证的工作契约与可变动作范围，可以包含运行中按新事实发现工作。它不要求提前写出所有子任务标题，也不是“可做任何事”。程序校验批准的输入引用、路径、职责/来源、工具和验收关系；缺少自动范围证明的操作保留为明确待决定项，不通过模型自己的“在范围内”声明放行。

调度角色交接按 Workflow 中明确授予的任期/委派规则进行；替换当前 Run 的用户选定主 Commander 仍遵循已有人工交接要求。其他受权子图角色的正常创建、授权内委派与结束无需冒充主 Commander 交接，也不重复打开已获授权的业务范围。

## 3. 冻结定义，版本化演化任务图

冻结与动态扩展同时成立：

| 固定或演化对象 | r8 语义 |
|---|---|
| WorkflowBundle、模板 compiled digest、角色/执行种类定义 | 仍绑定原部署版本；运行中不会因新的 active 模板而热更新 |
| 初始输入、用户授权和初始 Plan 摘要 | 固定可变范围、必须结果、预算/来源和调度 grant；不把未列出的合法子任务当作天然越权 |
| `TaskGraphRevision` | 每个已接受决定生成不可变图 revision/digest，记录父 revision、新增/替代节点、依赖与决策来源 |
| `SchedulingDecision` | 记录角色执行身份、grant、触发事件、所见 graph revision、输入摘要、动作、原因与接受/拒绝结果 |
| 已启动 Attempt | 固定 Task revision、输入、Profile/来源、工具与预算绑定；新图不能改写其运行清单 |

现有 PlanRevision 可以承载已提交图快照，或引用单独的 TaskGraphRevision；实现须有唯一的当前图引用，不另建两个可相互漂移的状态机。初始用户批准摘要不因每次增图重算为“用户新批准”；后续图 revision 引用原批准与有效 SchedulerGrant，区分 `user_approved` 和 `accepted_under_grant`。

新增子任务记录父任务/扩展集合、目标及来源材料、固定角色版本、验收义务、允许路径和父预算。运行中发现更多独立工作可以继续扩展。修改已启动任务的输入或职责只能形成后继任务/新 Attempt，并按需要取消或隔离旧执行；旧执行的产物、消费和迟到事件继续可查。

若要求改变用户目标、工具/来源/数据去向、硬预算或交付权限，形成具体授权变更并等用户批准；不依赖该变更的已承诺工作继续按原 grant 运行。资源不足、暂不可用和未知计量产生阻塞/排队，不把合法的任务需求自动改成授权外或强迫重新批准全部图。

## 4. 调度命令的接受与恢复

`SchedulingDecision` 至少包含 `decision_id`、幂等键、ExecutionRef、grant revision、Run/子图身份、expected graph revision、触发事件/输入摘要和声明式动作集合。自由 shell、Python/JavaScript 或任意管理 API 调用不能成为调度动作。Task ID 使用由可信服务按 decision/子项键生成或校验的稳定身份，重传不产生第二批任务。

接受顺序为：

1. 持久化/定位命令身份，校验认证主体、grant 链、未撤销状态和输入/动作范围。
2. 编译增量图，校验引用、普通依赖无环、有限返工、义务与产物影响；计算预览和可解释的资源请求。
3. 在短事务中 CAS 当前图和受影响子图 revision，提交图快照、父子关联、决定回执及 outbox。全部提交或全部不提交，不按资源空槽数截断图。
4. 可信准入消费已接受的派发决定；当前能力或资源不足时保存明确等待状态，条件变化后继续同一动作，不重复建任务。

同幂等键同载荷返回原结果，同键不同载荷拒绝。两个角色基于同一旧 revision 修改重叠范围时最多一个提交，另一个获得新 revision 和冲突原因；角色可在原 grant 内基于新事实重作决定，不要求用户替它解决每次 CAS 竞争。明确不相交的子图可由事务证明其读写集合后提交，禁止默默合并冲突依赖或覆盖对方结果。

重启恢复已提交图、决定、grant 撤销和 outbox，核对未确认的执行身份后再派发。角色调用已发送但响应未知时按原 ModelCall 核对，不能为取得“同一决定”重复调用模型并归零消费。提交成功而回执丢失时查询 decision ID；图不会重复扩展，恢复也不会因当前 active 已更换而迁移旧 Run。

## 5. 事件驱动与资源背压

用户输入、新材料、任务结果、阻塞解除等可信事件可以触发已配置的调度角色作一次有必要的判断。待处理事件与决定关联并幂等消费；订阅刷新、心跳或每个进度 tick 不自动调用模型。角色可以提交“这些任务满足依赖后派发”的持续指令，由引擎在事件到达时机械准入；资源释放只需唤醒等待队列，不要求主模型轮询或重复决定。

Karajan 不设置产品级固定 Agent/coding Agent 总数，也不在用户未配置时补一个默认 2/4 上限。并发实际受用户明确政策、上游并发/额度、宿主可验证资源、执行器能力和独占资源约束。资源事实未知时使用已授权的保守政策或显示缺口，不把“未设人数上限”解释为无限资源或无限消费。

有效任务全部保留于图中；暂不能准入的任务排队或背压，优先级来自已接受的调度决定及明确资源公平政策。队列批处理、接口分页和单次 payload 大小可以有工程限制，但必须支持续页/分批提交，不能将合法任务集截成前 K 项。资源政策限额需可解释来源，不能隐藏为产品默认人数。

每个可写执行工作区同时一个 writer 是冲突约束；不同隔离工作区可并行，不据此导出全项目只能一个或两个 Agent。两个任务请求同一独占写区时等待、由受权角色重划分或分配独立环境；不能绕过互斥，也不能把未完成任务直接丢弃。冻结候选的确定顺序集成与真实重叠执行分别记录。

## 6. 扩展集合、汇合与完成义务

动态 fan-out 建立 `ExpansionSet`：绑定父任务、grant、目标、当前成员 revision、`open/sealed` 状态与接收结果的义务。角色可按获准材料逐批提交成员；未封口时即使当前已知成员都完成，汇合也不能推断“没有更多任务”。角色通过当前 revision 的 `seal` 决定声明发现/拆分完成，可信服务验证必要发现步骤和结果覆盖，再冻结本批成员集。

已承诺的子图、必需输出及被引用产物不能通过删除节点、改名、改 optional 或减少集合成员来抹去。合法细化/替代须提供覆盖原义务的映射；旧节点可标 superseded，但其产物来源、消费和失败仍保留。依赖引用需要明确重绑定和失效处理，失败/取消/unknown 不会变成不适用或自动完成。

汇合针对已 sealed 的成员 revision 等待全部必需有效结果，并固定输入摘要。之后发现新工作只能新增受权扩展批次/图 revision；重新计算受影响汇合与证据，不能把旧汇合的通过套给新成员。Run 完成还要求所有可能贡献必需工作的扩展集合已经闭合、有效返工义务完成，并满足冻结的 report/patch/pr 产物目标。

报告和补丁仍按各自质量要求完成；PR 必须对最终候选重新执行必需机器 checks、独立 Review 和远端交付核对。调度角色不能删除这些 gate、让作者改名审查，或将旧候选证据绑给新图产生的内容。暂停、取消与未知尾账继续按既有生命周期处理，图变化不释放尚未核对的物理执行或消费。

## 7. 一个需求驱动的配置例子

以下为设计示意，不是已实现 schema。任务是检查并修复一组命令行工具的配置加载缺陷；用户授权的调度角色按固定仓库输入和缺陷材料决定如何划分，不使用前后端角色分类。

```yaml
workflow: repair-config-loaders
revision: 1
delivery_kind: patch
scheduling:
  role: role:repair-coordinator@1
  grant: grant:configuration-repair-scope@1
  decisions_on: [approved_input, discovery_result, task_result, actionable_blocker]
  actions: [expand_graph, bind_role, set_dependencies, set_priority, request_dispatch, seal]
work_contract:
  input: approved_repository_snapshot
  scope: [src/config-loaders/**, tests/config-loaders/**]
  required_outcome: resolve_confirmed_configuration_defects
  roles: [role:defect-researcher@1, role:repair-engineer@1]
  budget: budget:user-approved-repair
  resource_policy: policy:user-approved-host-and-provider
completion:
  join: all_committed_required_members_after_seal
  artifact: integrated_patch
  validation: checks:configuration-repair@1
```

在不同输入中，调度角色可以发现一个共性缺陷形成 1 项工作，或形成 3/7 项有独立输入和验收的工作；数字来自实际需求与决定，不是填入模板的 Agent 数参数。若当前资源只允许其中一部分同时运行，剩余成员仍留在图与队列中，资源释放后继续。新缺陷超出获批路径时仅对应扩权部分等待决定。

## 8. 验收与迁移

| ID | 动作 | 必须观察到的结果 |
|---|---|---|
| RS-AC01 任务驱动规模 | 同一 Workflow 使用三份分别适合 1/3/7 项工作的非前后端输入 | 授权角色实际产生不同子图、角色绑定与决定证据；不修改产品代码或预写三份固定图 |
| RS-AC02 原范围自动生效 | 角色连续扩图、委派和调整优先级/派发 | 命令通过 grant 校验后直接提交执行，不逐任务请求人工再批准；父子 grant/决定可追溯 |
| RS-AC03 资源背压 | 用户设置低于合法任务数的并发政策或触发真实资源短缺，再释放资源 | 全部任务保留，部分排队后续准入；无产品默认 K 截断，无无限吞吐或消费声明 |
| RS-AC04 越权与委派 | 请求超路径/来源/预算、无权转授权或越过授权链边界 | 拒绝或形成具体待批准变更；原授权内独立工作可继续，角色改名不授予权限 |
| RS-AC05 竞争与恢复 | 两角色冲突写图，重复同一命令，并在提交/启动回执处重启 | CAS 冲突可解释，同命令不重复扩图或派发，旧调用消费保留，恢复使用旧 Run 冻结定义 |
| RS-AC06 写区冲突 | 多个任务请求同一写区，同时另有独立写区任务 | 同区一 writer，冲突任务等待/重分配；独立写区可按资源并行，不出现全局默认 Agent 限额 |
| RS-AC07 Attempt 冻结 | 运行中角色修改图/分工，随后发布新 active 模板 | 原 Attempt 输入/Profile/权限不变；新任务/后继 Attempt 绑定新图revision，旧 Run 不追最新部署 |
| RS-AC08 汇合与义务 | open 集合当前成员完成，再增成员/seal；尝试删失败任务或已引用产物 | 未封口不提前汇合，扩展后旧证据失效；原义务不能被删图/optional/改名绕过 |
| RS-AC09 事件与用量 | 刷新页面、持续心跳、释放资源，再到达需要判断的新结果 | 刷新/资源重试不触发模型轮询；判断事件与角色调用对应，图调整不重置调用/返工/尾账 |
| RS-AC10 产物与 PR 门 | 在动态子图完成后交付 patch 或 PR，尝试跳过 PR checks/独立审查 | 按全部有效义务和同一最终产物验收；PR 不能借动态调度削减质量/独立性/交付权限 |

配置驱动与决定提交取得 C/U/P 证据；1/3/7 真正由所选模型判断、并行执行与真实来源另取 S 证据，PR 远端结果取 G。fixture 的图数量或配置中的 max 字段不证明真实角色判断，也不证明取消/隔离或吞吐上限。

迁移先增加 grant、调度决定、图 revision 与 ExpansionSet，再接已有编译、准入、outbox 和 Hub。旧固定图 Run 可保持原执行语义；已有用户明确批准的并发政策继续尊重，不能把用户设定值误当过时产品默认删除。历史默认两个 writer 的示例只作为固定场景证据保留，新 Run 不自动继承其产品默认。r7 的真实包、同源预览、pending/读回/active 部署与具体 Run 授权不变，初始预览须额外展示动态动作范围、委派边界和完成义务，运行视图展示当前图及每次受权修订。
