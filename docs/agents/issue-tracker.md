# Issue 跟踪与自动验收

[GitHub Issues](https://github.com/zhouy1017/Karajan/issues) 是任务状态和讨论的唯一来源。`dev` 是默认分支和日常集成基线；新实现分支从最新 `dev` 创建，新 PR 的 base 设为 `dev`。`main` 的发布安排不构成已满足开发任务验收的额外条件。

本流程依据 2026-09-06 用户授权：开发 Agent 可以自行核对验收、回填证据并关闭满足原范围的 Issue，无须逐票再次请求确认。合并权限仍按当前会话已有授权执行；本流程不新增任意功能 PR 的自动合并权限或付费模型调用权限。历史“合并由用户决定”约定限定的是合并，已合并且满足原范围的任务按本次关票授权处理。

## 当前设计变更的承接规则

2026-09-14 r6 新增外置 CLIProxyAPI 与自定义角色/Workflow，依据见 [治理增量](../planning/design-governance-20260909.md#r6-网关与可配置流程的承接)。P1–P4 是工程承接顺序，三角色到 PR 是内置模板；新 report/patch 工作流不关闭原 PR 交付范围。新增实现范围按 FR21–23、UX-AC15–18 和 GW/WF-AC 独立承接，不扩写旧候选为已完成；本地修订与远端发布分别记录。

r7 增加 FR24/25、UX-AC19–22 与 [WD-AC](../architecture/10-conversational-workflow-deployment.md)：对话 Agent 实际生成配置、图表同源迭代、精确确认、真实部署加载读回及适用 Run 执行。生成文件、发布定义、部署生效、执行开始和业务验收分开记录；一次已明确覆盖的部署并运行授权无须重复确认，已有原票也不会因此自动涵盖新范围。

2026-09-14 r8 增加 FR26/27、UX-AC23/24 与 [角色调度 RS-AC](../architecture/11-role-directed-scheduling.md)、[ADR 0008](../adr/0008-role-directed-scheduling.md)：Workflow 中明确获授权的 Commander 或自定义角色按实际任务决定拆分、绑定、依赖、扩图及派发规模。范围内 SchedulingDecision 经可信服务校验后自动提交 TaskGraphRevision，不逐子任务重批；更换定义或扩大 SchedulerGrant/原授权才请求新确认。旧定义/授权及已启动 Attempt 保持固定，动态扩展集合封口后才汇合，既有义务不因删图消失。

r8 产品不内置前后端分工或 Agent/角色/任务/并发人数上限。机器与上游实际容量、共享资源和用户明确预算/策略决定实际执行时机，资源不足时保留完整任务图排队，不截断任务或改写业务目标。新实现必须分别验证业务拆分、范围内命令实际生效、真实执行容量与排队恢复，不能把增加一个数量配置字段或模型文字建议算作调度完成。原发布 Issue/JSON 保留字节与摘要，新增范围独立拆票及记录证据，不回填成旧票已具备。

涉及 Commander Workbench 的设计、拆票或排期时，先读 [设计治理与承接矩阵](../planning/design-governance-20260909.md)，再读 [当前业务顺序](../planning/business-first.md)。P1–P4 是工作台承接顺序，r9 全量任务按就绪清单的实际依赖领取；M0–M4/DG、原 PRD、Issue 和候选失败是历史范围及证据基线。映射是承接关系，不表示取代或完成，旧父票的原验收和 native blocked-by 仍须保留。

UX 子票可以分别验收页面、持久状态和契约切片；P3 的两个无依赖 Task 并行与组合候选是原票的历史最小验收样本，可以在 #17 的完整交付 gate 之前独立实现，但不能关闭 #17、写成完整交付或成为产品默认人数上限。r8 动态调度与超出原样本的自适应任务图另按 RS-AC 验证。P4 必须把当前候选的 checks、独立 Reviewer、diff/head/PR 和限制分别绑定证据。新增任务不得把“未来阶段”当作依赖，也不得用旧候选的通过替代新候选核验。

用户固定的模型/来源及允许角色选择的集合必须原样进入批准版本；资格、能力和额度是硬 gate，阻塞时保留用户决定路径。获授权角色负责业务拆分和派发决策，可信程序校验并提交命令、执行资源准入、状态推进、幂等、恢复和收据；纯状态更新和队列唤醒不通过主模型轮询。此设计承接不扩大既有消费、合并或外部写入权限；现金 API、订阅外余额和现金后备仍按原边界暂停。

## 1. 固定范围并拆出可验收任务

1. 读取 Issue 原正文、验收清单、关联 PR 和依赖；将原范围作为验收基线。若原正文不完整，先记录可从已确认规格核对的要求和仍需澄清的缺项。
2. 产品父 Issue 保留完整需求并标记 `kind:requirement`；将可独立验收的实现、集成或真实资格切片建为 GitHub 原生子 Issue，标记 `kind:task`，并在双方正文保留链接。用原生 blocked-by 表达实际依赖；阶段路线图不自动等于可执行任务。
3. 每个子 Issue 写明具体输入、可观察行为、预期结果、修改范围、证据层级、依赖，以及明确留给父票或其他子票的工作。每项原验收条件都必须有归属；拆分不会删除父票要求。
4. 完整输入/输出、边界、原验收、责任和证据层级明确后标记 `spec:ready`；有已核验原生子 Issue 的票标记 `planning:decomposed`，正文列明各子票与剩余责任。已拆分不表示全范围完成。只有依赖可执行、已进入[当前业务队列](../planning/business-first.md)且可以开始当前叶子工作时，才同时标记 `status:ready` 与 `ready-for-agent`。依赖未完成使用 `status:queued` 并保留 spec 标记；纯实测被明确配置/授权/资格阻塞时用 `status:blocked`，不加领取标签。标签均不授予新增消费权限；可选 Bernstein 不进入关键路径。

已满足本地原语或离线行为原范围的任务可以独立关闭。完整 v1、真实来源资格或后续产品集成仅在原范围要求时才是该票的验收条件；后续新增要求另建关联任务。

## 2. 按证据验收

采用 [需求与证据审计](../implementation/requirement-coverage.md#1-审计状态和证据规则) 定义的 C（产品行为）、U（工作台）、P（本机执行）、S（真实服务）、G（GitHub 远端）证据层级。逐项将原验收条件与实际证据对应，保留 `not_run / passed / failed / unsupported` 结果。

每项证据至少记录：

- 对应验收条件、Issue / PR 链接和实现 commit；
- 可复现命令或操作、固定输入、预期与实际结果、报告或 CI 链接；
- 证据层级、日期、执行与复核者，以及适用范围和剩余限制。

拟合并 PR 先核对当前候选版本的 CI 和独立审查，包括本流程及模板等仓库管理变更。CI 通过只证明其实际覆盖的检查。源码、fixture、PR 创建成功或模型自述均不能替代行为验收。旧候选的通过不能直接升级新候选；改动后按影响补验并绑定新 commit。

实现与真实资格分别记录。假依赖可以证明其适用层级的本地行为，不能证明真实认证、计费、隔离或另一 Profile 的资格。涉及真实来源时补充 Profile / runtime revision、OS / 隔离、配置摘要和观测范围，只保留 secret_ref 或脱敏身份。取消或本地停止后保留无法确认的远端状态为 `unknown`；关闭任务也不抹除该事实。

验收结束时，每项原条件都有证据和结果；缺项、失败及阻塞须明确记录。调查票可按原调查目标完成并记录 `failed / unsupported` 发现，对应产品能力仍保留未满足状态。

## 3. 将 PR 与关票动作连接

PR 正文使用 [PR 模板](../../.github/pull_request_template.md)：写清可观察变化、逐项验收结果及限制。

- `Closes #<编号>` 仅指向本 PR 合入 `dev` 后完整满足原验收范围的子 Issue 或独立任务。
- `Refs #<编号>` 指向产品父 Issue、依赖票和仍有剩余要求的任务。只有父票所有必需验收条件均已满足时，才能将父票放入 `Closes`。
- 候选验收通过但 PR 尚未合并时，Issue 保持 Open 并标记 `status:awaiting-merge`，记录候选 commit 和 PR 链接。
- 合并后查询远端，确认 PR 已进入 `dev`、最终候选检查有效、原验收条件完整满足，再核对自动关票结果。缺少 Closing 关联的历史任务可以由 Agent 回填验收结论后直接关闭。

GitHub 的 Closing 关键词在 PR 合入默认分支时触发，因此必须在合并前完成证据核对。验收不再满足时，先移除相应 Closing 关联并回填缺项；若已误关，重新打开并说明原因。合并提交引入额外行为变更时，按影响补验后再关闭。

## 4. 同步父票与交接

每次切片合并、验收结论变化或发现阻塞后，更新对应 Issue 正文中的以下三项，保留原始需求和验收清单：

- **已完成**：已进入 `dev` 且验收通过的范围、子票、PR 和证据。
- **剩余工作**：原范围中尚未满足的条件及责任子票；实现进展与真实资格分别列出。
- **阻塞**：具体原因、依赖链接和解除条件；没有阻塞时写明“无”。

当前状态使用 `status:queued / status:ready / status:in-progress / status:blocked / status:awaiting-merge / status:completed` 标签，并同步正文；同一任务只保留一个当前状态标签。`queued` 表示仍需完成但当前未分派，具体技术阻塞继续写在正文；`in-progress` 须有当前负责人和正在执行的工作。已验收且进入 `dev` 的任务关闭时标记 `status:completed`。子票关闭后重新核对父票验收清单；只有所有必需条件通过且进入 `dev` 才关闭父票。交接时先说明新增可用行为，再给出剩余条件与下一步。

清理过时安排时，保留原验收正文、失败证据和已有候选，将失效的调度/状态快照折叠为历史，顶部只保留当前安排。有效需求移入队列不算完成。只有确认重复或已被取代的任务才用 GitHub `not_planned` 关闭，先逐项写明原要求的承接 Issue；不贴 `status:completed`，也不用 `Closes` 制造交付记录。发布快照保留原字节和摘要，以新修订记录当前清理结果。

本地 PRD 与 Issue Markdown 是版本化规格和发布正文快照；发布清单保存实际 GitHub 编号、URL 和关系核验结果。规格修改同步并注明 revision；远端状态按以上流程回填，不能把本地文件状态当成远端任务状态。
