# 已有 Run v2 计划的 Web 审阅与确认

本切片把已持久化的 v2 计划接入项目的「需求与计划」页面。用户打开已有 Run，看到该计划的完整执行授权，勾选已审阅后确认具体版本。新需求表单继续使用原有 v1 创建命令；没有新增 execution policy 登记、来源启用、模型调用或实际派发入口。

## 用户看到的范围

v1 与 v2 明确标识。v1 保留原计划审阅与批准行为。v2 从 Run 自己的 `configuration_snapshot`、`execution_policy_snapshot` 以及最新计划的 `routing_binding` 读取材料，不读取项目后来发布的规则来替换旧计划，也不把授权 ceiling 当作这次批准的范围。

v2 显示读取/修改路径、检查与交付分支；精确 Profile 版本、模型、账户、调用通道、执行器版本与计费路径；允许通道的服务商和数据去向；工具与权限映射、必需能力及工具沙箱要求；原币授权限额、单次尝试时长、质量修复轮数。引用的运行预算上限另列，避免与本次收窄后的金额或单次时长混为一谈。金额保留服务端十进制字符串。

每条规则分别列出普通阶段许可、普通配置组的精确成员，以及质量升级组的原始序号、组名和精确 Profile 版本；未授权或空成员明确显示。任务列出版本、角色与 Commander 职责、就绪状态、难度、风险、路径、领域、能力、工具、上下文输入上界、时长、依赖与验收标准。页面还显示政策中的风险映射、路径下限、输入记账定义、输出预留与总上下文上限。

「核对固定版本与授权摘要」折叠区提供政策所属项目/登记者/id/revision、工具/风险/上下文子政策版本、Rulebook 版本与正文摘要，以及本计划、配置、授权和路由绑定的四个摘要。Profile 或通道中未声明的来源信息明确标注未配置或未声明，不补模型、计费路径或资格。

## 确认协议与刷新行为

继续使用已认证的 `GET /v1/runs`、`GET /v1/runs/{id}` 和 `POST /v1/runs/{id}/plan-approval`。现有服务端路由已支持 v2，未新增桥接路由。v2 批准正文显式携带 `schema_version=karajan.approve-plan.v2`、term、plan_revision、plan_digest、configuration_digest、authorization_digest、routing_digest；请求同时携带 CSRF 与幂等键。仅用户勾选当前完整范围后出现可用的确认动作。

材料缺失、未知协议、v1 标识混入 v2 绑定、政策身份/配置不一致，或冻结任务要求与计划正文不同，都不提供批准入口。前端检查只用于保证页面展示完整，批准权仍由服务端的 owner、term、版本和摘要检查决定；前端不重算或创建 grants。

每次重新读取 Run 都先撤销旧展示与勾选。409 或 422 后重新读取，读回相同字节也需要重新审阅；读取失败时不会恢复旧批准按钮。切换 Run、项目或登录会话不带走原勾选，旧项目的迟到响应不会替换当前计划。发送结果不确定时，用户在同一视图重试会复用原正文及幂等键；明确版本冲突后使用新的确认身份。

## 验证与边界

前端交互首个失败是旧页面没有 v2 完整范围；修复后验证精确 v2 请求与显式确认。另一个实际红灯是 409 后读取失败仍保留旧批准按钮，现已撤销旧视图。保留这两个原输入的 before XML，不把直接通过的边界测试说成红灯。

`ProjectRuns.v2.test.tsx` 通过用户操作和 HTTP 边界替身检查完整展示、版本拒绝、范围/任期变化、重试身份与迟到响应。`tests/web/test_v2_approval_workbench.py` 使用真实本地 Git、公开 Registry/RunPlanner 和认证 HTTP：显式 fixture 规划回执产生有效 v2 计划，读取冻结材料、批准和重放，并验证旧协议/缺摘要/错误版本/陈旧计划不改变 Run。现有 v1 与新建需求回归保留。

这一步没有实现 trusted builder、实际 RouteDecision、资源准入、Attempt 或启动 outbox 接线，也没有启用 Profile 或授予执行资格。确认后的 `dispatch_enabled` 仍为 false；上下文数值是批准的输入上界，真实输入及工具执行仍需后续执行前核验。最终检查数量与源码绑定记录在本切片的 `examples/v2-approval-workbench/author-freeze.json`。
