# M1：需求、计划确认与人工交接工作台

本切片把 [Run 计划领域](m1-run-planning.md) 接到已认证的本机 Web 工作台，关联 [M1-02 #12](https://github.com/zhouy1017/Karajan/issues/12) 和 [M1-06 #16](https://github.com/zhouy1017/Karajan/issues/16) 的入口部分。它能够保存需求、显示已存在的确切计划及授权，并记录用户的计划批准和 Commander 交接决定。

模型派发尚未接通。保存需求不会生成示例计划；批准计划或交接仍返回 `dispatch_enabled=false`，真实模型资格保持 `not_run`。本切片没有实际模型请求和现金 API 调用，也没有创建业务 PR。用于浏览器验收的脚本化计划放在明确命名的“离线验收样例 · 不调用模型”项目，不能视作模型输出或真实准入证据。

## 产品入口

用户登录后，在项目卡片选择“需求与计划”。“新建需求”读取项目的当前配置和批准 Profile 集合，要求填写目标、逐条验收标准和允许读写的相对路径。选定主 Commander 后，提交冻结的项目 revision、configuration digest、参与者、授权范围、原 Run 预算和 PR 目标；独立审查自动保留为必需条件。

首个页面只选择一个主 Commander。顾问与交接候选可以由领域 API 在创建 Run 时指定，完整多参与者编辑留待后续工作台；页面不凭空产生替任者。

现有需求按项目列出，打开时读取持久快照。计划卡展示全部子任务、前置依赖、必需/可选、T0 待澄清状态、复杂度、风险、路径和验收标准；授权卡展示允许模型配置及版本、读写范围、必需检查、PR 目标和原币/次数/时长预算。只有取得固定预算且当前 Commander 的最新计划尚未批准时，才提供批准动作。批准只发送已显示材料的五项确切绑定，不能在按钮请求中改写计划。

交接卡展示指定候选和 Profile 版本、检查点说明与文件引用/摘要、固定规划预算及提案的资源说明。当前余量和文件实体尚未接通核验，页面明确标注；资源说明不当作账本事实。候选 Profile 或固定规划预算缺失时禁止确认，仍可选择保留当前 Commander。未答复不发生切换；拒绝保持旧 term；当前提案确认才保存指定新 term。

HTTP 409 会重新读取当前快照并要求重新审阅；不会用旧摘要自动批准新版本。动作结果与当前状态分开：成功回执后仍重新读取 Run；`executing` 在本阶段只显示为“计划已确认，等待满足执行条件”。

### 保存结果未知时的处理

需求创建在发送前，把原 body 与 `Idempotency-Key` 写入并读回校验版本化 `sessionStorage` 记录。命名空间绑定项目 ID 和当前稳定 CSRF 的 SHA-256；不持久化原 CSRF 或认证材料。网络异常、5xx、409/422 和响应解析失败均保留原请求，表单锁定内容，仅由用户点击“核对保存结果”重试原 body/key，不自动发送。

收起后重开或刷新时恢复同一待核对记录；项目配置变更也不替换原请求。只有成功响应含有效 Run ID 时才清除匹配记录，旧请求的迟到响应不能删除后来新建需求的记录。存储损坏、不可用或范围不符时不发送。

恢复范围限同一标签页、同一认证会话。重新登录后不同命名空间不自动重放旧命令；关闭标签页/浏览器后不保证恢复。这不等于后端恢复或全浏览器恢复。当前没有独立“服务已证明未创建”的解除契约，明确拒绝也先保留待核对记录，不由前端猜测可新建第二份需求。

## 认证与 HTTP 边界

新增入口继承 Host、Origin、本机 session、CSRF、JSON 大小和无缓存边界：

| 入口 | 作用 |
|---|---|
| `POST /v1/runs` | 以 `Idempotency-Key` 创建需求，身份来自已认证 owner |
| `GET /v1/runs?project_id=…` | 只列出当前 owner 的项目需求 |
| `GET /v1/runs/{id}` | 返回 owner 的当前快照和 revision ETag |
| `POST /v1/runs/{id}/plan-approval` | 批准确切 term、plan revision 及三项材料摘要 |
| `POST /v1/runs/{id}/handoff-decision` | 对确切提案和 term 保存 approve/reject |

Web 没有模型计划提交、资源回执内容注入或交接提案创建路由。生产 `RunPlanner` 没有 fixture admission reader；后续可信协调器须自行完成身份映射和真实资源接线。用户或模型提供的 JSON 不能因此变成控制端身份。

## 已取得的验证

2026-09-05 Windows 上，Run/候选/Web 组合通过 **141 项测试、3 项 POSIX 专用测试跳过**；2 项警告来自既有 Starlette 测试客户端的依赖弃用提示。Ruff 和 14 个源文件的 strict mypy 通过。候选的 3 项 POSIX 权限变体另在真实 WSL2/ext4 通过，详见 [候选验证](m1-candidate-validation.md)。

新增 HTTP 的 3 个公共流程分别覆盖真实临时 Git/SQLite 中的需求创建与重开、确切计划批准/幂等重试，以及人工交接拒绝/接受/旧确认拒绝。测试中的规划 receipt 和计划明确由脚本化测试依赖提供；请求实际经过认证 HTTP 边界，没有直接改私有表。

最终前端 **17 项交互测试**通过（6.83 秒），其中需求创建有 9 项；TypeScript、全目录 Prettier 和 Vite 生产构建通过。未知保存的四轮实际红→绿覆盖：修改后产生第二请求、卸载丢失原命令、缺摘要能力导致页面异常，以及旧卸载请求的响应清除新记录。存储失败/损坏、项目/会话隔离、畸形成功响应保留等补充变体通过；这组故障测试的 HTTP 是可控假边界，不冒称真实网络故障演练。

交接 UI 审查发现材料不足后，补了 3 个实际红→绿变体：正常材料可见、缺 Profile 禁确认、缺预算禁确认。补充计划依赖及持久批准状态也经历失败断言再通过。独立复验确认交接卡修复。

真实浏览器在本机服务上已完成：登录，打开已登记的离线样例，核对授权与零现金预算，确认计划，刷新后读取同一批准版本，拒绝第一次交接并观察 term 1 保持，确认第二份新提案并观察指定替任者进入 term 2。三个任务及其依赖仍保持，全部过程没有启动模型。

最终构建另在实际表单新建“浏览器验收：保存带范围的需求”，通过界面选择已批准的 fixture Profile，填入两项验收、`src/tests` 读取范围和 `src` 修改范围，保存后显示同一需求且“尚未收到 Commander 的计划”。没有为正常需求生成演示计划。

对应固定样例材料：project `a02f2f5a-be94-497f-ae60-700ac5cad7a1`，Run `2c1802c3-146b-4174-916f-046827990b4c`，计划摘要 `b83f79f78c5102af977df9b9126dd4784aa11cca8182dbca5bb62ecec6b06ef4`，检查点内容摘要 `973d78dbcbec622b5c486104a0530475bb2ff19167fe09e96bc7ba1d711a8b9d`。这些是本地测试身份，不是外部服务资格。

完整 M1-06 仍需 Run/Task/Attempt 与交付/资源的统一快照和持久事件、SSE 重连、暂停/取消/恢复及当前阻塞动作。当前页面没有伪造这些状态或实时配额余额。
