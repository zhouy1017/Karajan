# Commander 工作台设计

版本：2026-09-09。状态：设计基准，尚未表示产品实现完成。

Commander 工作台把 Karajan 的首演路径呈现为一个持续可访问的控制入口：用户先打开仓库和会话、选择已配置的高级 Commander 模型与来源，在 Commander 对话中描述需求；Commander 读取只读仓库上下文、提出完整且可编辑的默认任务分工；用户可以一键接受，也可以按需编辑角色、模型、来源和依赖，再批准同一个版本；工作台随后显示并行 Worker、组合候选、检查、独立 Reviewer 和 PR。用户不需要每次运行前填写配置、资格或预算表单。

## 设计依据与边界

信息架构参考 [Bernstein GUI screens](https://bernstein.readthedocs.io/en/latest/gui/screens/) 的任务列表、详情抽屉和 Agents 视图；工作模式参考 [Toil offloading skill](https://github.com/zhouy1017/toil/blob/main/src/toil/_assets/skills/toil-offloading/SKILL.md) 的主模型分解、委派和验收。Bernstein 的 [per-step routing](https://bernstein.readthedocs.io/en/latest/workflows/per-step-routing/) 主要描述 Claude 兼容模型的 model/effort 路由，不能推导出跨来源能力；Toil 的固定 Sol/Deepseek/Luna 与命令行工作流也不能当作现成桌面 UI 或资格证据。

这次设计选择工作台的观察和控制形状，不替换 Karajan 的执行底座。Commander 负责判断是否拆分、如何委派、何时建议升级和是否接受验收；可信协调器负责机械调度、权限/额度核验和状态提交。系统不存在第二个模型主控。

## 页面骨架

### 仓库与会话导航

顶部导航始终显示当前仓库、目标基准/分支、Run 和计划版本。切换仓库或会话先加载持久快照；若没有可恢复的 Run，显示空态并把“与 Commander 开始”作为主入口。切换不会丢失未发送的对话草稿，也不会把另一个仓库的任务混入当前看板。

### 中央 Tasks / Agents 看板

中央区域是当前 Run 的主工作面。任务卡至少显示任务标题、角色（Commander、Worker、Reviewer）、显式模型与来源、状态、依赖摘要、当前 Attempt 和最后一条可观察结果。Agents 视图按 Agent/Attempt 展开同一事实，Tasks 视图按需求和依赖组织工作；二者联动选择同一详情。

看板支持按角色、模型、来源和状态筛选，也支持只看阻塞、可运行、运行中、候选或已完成任务。筛选只改变视图，不改变调度。并行任务各自显示独立写区、Attempt 和结果；看板明确标出“可并行”“等待依赖”“组合中”，避免把并行误解为共享工作区覆盖。

### 右侧详情面板

选择任务、候选或 Agent 后，右侧面板提供固定的五个可切换页签：

- **Diff**：候选相对批准基准的文件变更、来源任务和冲突；空态说明尚无候选。
- **Checks**：检查命令、开始/结束事实、结果、证据版本和未知状态；运行中显示等待而非伪造通过。
- **Review**：独立 Reviewer、审查输入候选、verdict、问题和修复轮次；未启动时显示原因。
- **Logs**：按 Attempt 和时间查看可追溯事件、权限答复、路由决定、消费核对与错误；秘密不出现在日志中。
- **Dependencies**：前置任务、阻塞原因、可运行条件、集成顺序和受影响的旧证据。

详情面板在断线重连时先展示快照，再接收后续事件。任何用户动作都绑定仓库、Run、计划版本和当前状态；过期动作返回具体原因，不静默覆盖新状态。

### 持久 Commander 对话

Commander 对话是工作台内可从导航和任务详情返回的持久控制入口，不是一次性的资格/预算表单。对话上下文包含当前仓库、需求、未决问题、计划版本和看板选择；用户可以从任务卡跳到“请 Commander 解释此阻塞/重划分此任务”，也可以回到对话修改需求。

Commander 的建议以可编辑任务图呈现：任务目标、角色、模型、来源、依赖、验收和风险都可逐项修改。用户明确绑定和依赖后，批准动作显示将要启动的版本摘要；批准提交的版本号必须与页面正在显示的版本相同。计划变更生成新版本并说明受影响任务，旧候选和证据不会被冒充为新版本结果。

## 首演交互

1. 用户选择或打开目标仓库和会话，选择高级 Commander 的模型与来源；工作台显示仓库基准、该选择的可用状态和可恢复 Run。
2. 用户进入持久 Commander 对话，描述小需求、约束和验收；Commander 只读目标仓库并提出完整默认任务分工。
3. 用户在任务图/看板中接受默认分工，或按需编辑任务角色、指定模型与来源、依赖、检查和 PR 权限，然后查看范围、资源影响和待解决问题。
4. 用户批准当前计划版本。批准后可信协调器按依赖启动两个无依赖 Worker 的独立 Attempt；每个 Attempt 固定其批准的 Profile，不热切换运行中的 Attempt。
5. 两个 Worker 结果组合为确定候选；检查针对冻结候选运行，独立 Reviewer 从该候选和证据开始审查。修复或重派产生新 Attempt，并保留原 Attempt。
6. 右侧面板显示 Diff、checks、review、logs、dependencies 和 PR 状态；PR 创建、CI 和用户合并分别呈现。

首演以并行任务看板为核心交互。它不把真实能力、来源资格或预算状态写成已通过：页面只显示已知事实及其来源/时间；额度 unknown 在既有有限保守授权内按该边界运行，超出边界时等待或阻塞。

## 路由、授权与改派

首次建立必要的默认设置和认证后，工作台复用用户已授权的集合。日常入口不要求用户手填内部 JSON、资格矩阵或 Rulebook；需要改变这些内容时才进入设置/规则页面。权限和预算仍是运行约束，未知额度不显示精确余量，现金 API 暂停保持暂停。

用户显式指定的角色、模型、来源和依赖优先于默认规则。若指定配置不具备所需能力或已知额度不足，工作台显示缺失能力、当前事实、替代候选（若在预先批准集合内）和所需用户选择，并等待可行选择；系统不静默替换或提价。额度 unknown 先显示其来源、时间和适用边界：已有有限保守授权时按该授权准入，否则等待核对或用户选择。自动切换只可发生在用户预先批准且当前合格的集合内，并为新 Attempt 保留原任务目标、风险、消费和原因。

模型按任务复杂度选择。便宜模型可承担边界明确的普通编码和检查；高级 Commander 用于理解、拆分、升级建议和验收判断，不承担普通编码或轮询。改派只作用于尚未启动的任务或停止/隔离后的新 Attempt。运行中的 Attempt 的模型、来源、工具权限和计量路径均保持不变。

## 状态与异常行为

| 状态 | 工作台表现 | 用户可做的事 |
|---|---|---|
| 加载 | 导航保留仓库/Run 标识；中央看板显示快照占位，详情页显示正在读取的页签 | 等待或切换已持久会话；不能批准未知版本 |
| 空态 | 没有 Run 时显示仓库基准、认证/资格摘要和“与 Commander 开始”；没有任务时说明任务图尚未提出 | 开始对话或打开已有会话 |
| 运行中 | 卡片显示 Attempt、固定模型/来源、依赖进度和最后事实；检查/审查显示进行中 | 查看日志、依赖和 diff；暂停仅停止新派发/交付，取消请求实际停止并等待核对 |
| 阻塞 | 卡片置顶具体 reason、影响任务、所需选择和可恢复条件；超出保守边界的额度/能力 unknown 显示核对中 | 选择已批准候选、补认证/额度、修改计划或等待外部事实；不能绕过验收标准 |
| 恢复 | 重连先回放持久快照，标明 running/exited/unknown 和待核对消费/远端结果 | 继续有效动作；对 unknown 先 inspect/核对，不能因 UI 超时重复启动或重复交付 |
| 候选/交付 | Diff、checks、review、PR 分栏绑定同一候选版本；未通过或旧证据明确标注 | 查看问题；在已批准的有界轮次和集合内继续修复/改派，或自行处理 PR 合并 |

## 可检验的 UX 验收

以下 UX-AC 是对既有产品 FR 的新增可观察表达，不删除或重写历史 PRD-AC01–06，也不宣称当前已经实现。

| ID | 前提与动作 | 可观察结果 | 原 FR 映射 |
|---|---|---|---|
| UX-AC01 进入工作台 | 打开已登记仓库和会话，刷新一次 | 顶部显示同一仓库/基准/Run/计划版本；中央先快照后事件，详情不混入其他 Run | FR01、FR17、FR18 |
| UX-AC02 持久 Commander | 选择高级 Commander 模型/来源，从空态开始对话，再从任务详情返回 | 对话保留需求、未决问题和计划版本；Commander 提出完整默认分工，用户可一键接受或按需编辑；入口不是重复填写资格/预算表单 | FR03、FR12、FR17 |
| UX-AC03 可编辑分工 | Commander 提出至少两个无依赖任务，用户修改角色、模型、来源和依赖 | 看板显示修改后的任务图和资源影响；批准前不启动 Worker；批准绑定当前版本 | FR04、FR05、FR13 |
| UX-AC04 并行首演 | 用户批准包含两个无依赖 Worker 的同一版本 | 两个独立 Attempt 可同时进入运行中；每卡显示固定 Profile/写区；任一结果不会覆盖另一任务 | FR07、FR13 |
| UX-AC05 详情联动 | 选择任一 Task、Agent、Candidate，依次查看五个详情页签 | Diff/checks/review/logs/dependencies 都绑定同一对象、候选和版本；无证据处显示空态或 unknown | FR14、FR17、FR19 |
| UX-AC06 显式绑定优先 | 用户指定模型/来源能力不可用，或额度 unknown 且超出既有有限保守授权边界 | 能力不足时显示具体原因和预先批准的可行选择并等待用户；额度 unknown 在既有保守边界内显示事实并按边界执行，否则等待核对；均不静默替换、不提价 | FR02、FR06、FR09、FR10、FR11 |
| UX-AC07 改派边界 | 运行中 Attempt 请求更换模型；停止后为同一任务选择合格替代 | 运行中 Attempt 的 Profile 不变；新选择只生成新 Attempt，保留原因、交接包和消费记录 | FR07、FR11、FR15 |
| UX-AC08 候选到 PR | 两个 Worker 结束，checks 和独立 Reviewer 读取冻结候选 | 看板/详情能追溯组合顺序、check evidence、review verdict、diff 和同一 PR；PR 创建不显示为 CI/合并成功 | FR14、FR19、FR20 |
| UX-AC09 过期动作 | 计划已变更或 Run 已恢复后提交旧版本批准/重派动作 | 动作被拒绝并说明当前版本/状态；旧证据保留为历史，不改变当前 Run | FR04、FR05、FR15、FR18 |
| UX-AC10 恢复与未知 | 断线或重启时存在 running、unknown 或待核对远端结果 | 页面先显示快照和核对状态；不以 idle/超时当作成功，不重复 spawn、消费或 PR | FR15、FR17、FR18、FR19 |

## 实现状态与范围治理

本文件描述 2026-09-09 的设计基准。页面已有部分需求保存、计划展示和精确批准能力的事实，仍以 [当前业务顺序](../planning/business-first.md)、实现文档和需求覆盖审计为准；本设计中的并行首演、真实来源资格、完整看板和 Candidate→checks→Reviewer→PR 证据链，在对应验收完成前都必须标为未完成或阻塞。

实现切片应引用具体 UX-AC 和原 FR，不把静态卡片、模型自述或离线 fixture 当作真实执行、额度或来源资格证据。任何范围变更同步更新本文件 revision，并保留原 PRD、Issue 和 ADR 的历史链接。
