# Commander 工作台设计

版本：2026-09-16 r9。状态：在 r8 对话式 Workflow 与授权角色调度基础上，新增用户要求的同一 Commander 会话内按角色 Agent、任务、模型及实际底层 provider 查看 token 用量；新增统计与完整产品行为仍待实现与验收。本文规定用户体验，不把配置示例、设计图或历史候选当作已实现能力。

Karajan 工作台是设计、部署和运行多来源 Agent 流程的持续入口。用户在 Hub 向 Workflow Designer 描述要求，Agent 编写真实声明式配置，服务端从同一配置生成流程图、角色/步骤表与差异；用户用文字或字段修改后，确认准确版本，由可信部署器将其加载到 Karajan 引擎。用户也可以直接选用已部署流程，提供输入并批准运行，无需每次重新设计或调用规划模型。

角色职责、步骤、依赖、条件、并行汇合、人工节点和有限返工均可配置。Workflow 中明确获授权的调度角色可以是 Commander 或自定义角色，由它按实际任务决定拆分、角色/模型绑定、依赖和派发规模；Karajan 不按前后端类别预设分工，也不内置 Agent、角色、任务数或并发人数上限。流程可交付 report、patch 或 pr；Commander/Worker/Reviewer 是代码交付模板中的角色，两个 Worker 并行到 PR 仅保留为历史最小验收场景。P1–P4 表示工程承接顺序，不规定所有 Run 的运行拓扑或数量上限。

## 职责与产品边界

- **Workflow Designer 与调度角色**：Designer 是 Hub 的流程创作模式，可独立绑定模型、来源与职责；Commander 或其他自定义角色可按 Workflow 中明确授予的调度权限进行业务拆分、绑定、依赖调整和派发决策。创作可先于目标 Workflow 和 Run 存在，使用独立的创作身份与已授权预算。同一 Run 可授权多个角色管理不同范围，用户选定主 Commander 的有效任期仍唯一；用户授予权限，角色可按明确委派规则派生权限子集，在范围内提交可自动生效的调度命令。增加或重命名角色不复制任期、调度权或用户批准权。
- **可信配置与部署服务**：保存版本化文件，校验/编译并生成同源预览；收到准确确认后，物化 pending 配置，取得调度器加载与读回证据，再条件发布 active 版本。模型文字和文件保存都不能自行改变生效状态。
- **可信协调器与执行器**：协调器验证调度角色身份与授权，校验并提交运行图修订，负责资源准入、依赖推进、幂等与恢复；业务拆分和派发决策来自获授权角色。受控 runtime 执行模型工具调用及本机任务。图表、Hub 与详情读取同一事实源，刷新状态不调用模型。
- **外置 CLIProxyAPI**：负责 provider 登录、凭据与协议转换。Karajan 管理连接、模型绑定、受控调用与账本；网关不拥有工具权限、工作区或调度权。原生专属能力可由显式兼容 Profile 提供，不作静默后备。

部署对象是 Karajan Workflow，不包括部署 CLIProxyAPI、网站或外部服务，也不默认创建定时任务。report/patch 按自身批准的产物和质量要求完成；pr 必须通过当前候选机器 checks、独立审查和交付授权，合并由用户决定。独立性根据实际作者、Attempt 与上下文等证据判断，不能靠角色名称取得。

技术契约分别见 [网关](../architecture/08-provider-gateway.md)、[角色与 Workflow](../architecture/09-configurable-workflows.md)、[对话设计与部署](../architecture/10-conversational-workflow-deployment.md)、[角色主导调度](../architecture/11-role-directed-scheduling.md)、[会话用量与实际路由](../architecture/12-conversation-usage-accounting.md)。早期 UI 参考和设计演变由 [治理索引](../planning/design-governance-20260909.md) 与 ADR 保留，活动界面以本文为准。

## 页面骨架

### 项目与会话导航

左侧按“项目 → Commander 会话”组织，项目与会话使用稳定 ID，显示当前选中对象，支持展开/折叠、最近会话恢复和新会话入口。项目名称或分支文本不能替代身份。没有会话的项目提供“开始设计流程”和“使用已部署流程”；没有 Run 的会话仍可保存讨论、配置草稿与部署记录。

顶栏始终显示项目与当前会话；选择运行后再显示 Run/计划版本，涉及仓库修改时显示基准/分支。设计模式显示配置 proposal revision 与部署目标，不能把不存在的 Run、候选或分支伪造为默认值。长名称可省略但能查看完整内容。

切换前保存消息、未发送草稿、选中对象和配置编辑状态；返回时恢复对应设计版本、部署、模型来源、Task/Attempt 和反馈事实。顶栏、Hub、详情与操作目标一起切换。异步返回校验 Project/Conversation/Run 或 Deployment 身份，不能覆盖另一项目视图。导航、折叠和新建都不暂停、取消、批准或派发任务。

### Hub 主工作面

Hub 持续保留对话，内联显示流程建议、同源预览、待确认操作、部署回执及结果。相邻任务区显示当前选定 Run 的任务缩略卡片，阻塞和待用户决定项优先。卡片包含标题、自定义角色或确定性执行种类、固定模型来源（适用时）、状态与最近可信进展；长日志和完整证据从详情展开。

在设计模式，用户与 Designer 迭代 WorkflowBundle；在运行模式，用户可以查看当前运行图、原授权、历次扩展的决策依据、产物、反馈和问题。使用既有模板时，可信编译器可直接根据输入形成初始实例计划；定义含动态调度步骤时，由获授权角色按实际需求继续拆分，不强制所有流程先调用 Commander。需要设计、拆分或调整派发等业务判断、解释阻塞或明确要求总结时才发起受预算约束的模型调用；结构化状态和结果在无模型调用时同样可见。

确认后仍停留 Hub。部署结果显示生效版本、目标与回执，运行结果按 report/patch/pr 展示成果、问题、质量证据和下一步。模型总结引用这些事实，不能覆盖失败、缺失证据或未知状态。任何新版本保留原建议、原批准与原结果，不冒充为新版本通过。

Hub 常驻当前会话的 token 用量摘要与“用量”入口；摘要覆盖该会话全部 Run 和无 Run 的对话/创作消费，不随任务区选中 Run 而悄悄缩小。用户可在同一对话展开分组和调用明细，继续保留消息、草稿与任务上下文。

### Workflow 设计与同源预览

Workflow 入口打开持久设计对话。用户描述目标、角色和协作方式，或要求在模板上修改；Designer 读取项目内允许的角色、执行种类、模型绑定和约束，生成包含 manifest、Workflow 与角色定义的真实配置包。用户无需先学 schema 或填写完整表单；影响执行的缺项、假设和能力限制必须可见。

流程图、角色/步骤表、实际文件与配置 diff 由同一包的编译结果生成。表格展示职责、模型来源、输入输出、依赖、工具约束、完成目标和部署限制；图展示分支、并行/汇合、人工节点及返工边界。点击图节点或表格行可以定位对应配置项，并继续用文字修改。

文字、表格或文件修改都产生新的配置 revision，重新校验与编译，旧预览立即过期。比较视图说明相对上一版和当前 active 版本的变化；迟到的 Designer 输出不能覆盖用户更新。图表不维护另一份流程状态。完整拖拽画布可以后置，同源图、表、文件与实际部署是必需体验。

Designer 生成、自动纠错与重试累计计入创作会话的调用、时间、次数和预算边界；新 proposal、重启或换模型不重置。达到上限或发送结果未知时保存配置与诊断，等待有效决定或核对，不能无限修复直到显示绿色。

角色可以从模板复制或新建，编辑职责、说明、输入输出契约、完成标准、所需能力和工具约束。工具约束是上限要求，不是用户授权；有效权限仍取项目、Run 批准范围与执行能力的交集。角色发布不修改旧 Run，不能借“Commander”“Reviewer”等名称取得受保护额度或独立审查资格。

### 获授权角色的自适应调度

Workflow 配置明确哪些角色获授 SchedulerGrant，以及允许的任务范围、角色/模型集合、工具与写区、依赖调整、产物目标、委派边界和资源授权。可以有多个有效授权角色，重叠图修改通过明确归属与 CAS 版本比较处理，不由最后返回的角色覆盖其他决定。用户批准的是这份定义、初始输入/计划和调度范围；不要求预先列尽运行中才能发现的全部子任务。角色根据实际任务与已接受结果提交 SchedulingDecision，包含新增/拆分任务、角色绑定、依赖及派发命令。范围内命令经可信服务校验后自动提交新 TaskGraphRevision 并推进，不逐子任务再次弹出批准；未获授权角色或过期任期不能通过同样接口调度。

扩大业务范围、允许来源、工具/写入权限、预算或其他原授权边界时，显示具体差异并等待用户确认；原范围内任务可继续。定义与原授权保持冻结，运行图以独立版本记录每次决定和影响；新图不覆盖旧图，也不热改已启动 Attempt。动态 ExpansionSet 明确封口且全部必需结果齐备后才汇合；已承诺的任务、产物和检查不能靠删图或改为可选抹掉。旧结果不能自动满足变更后的输入或证据要求，修复、重试和消费累计记录不会因拆出新任务重置。

角色决定业务上需要多少任务与并行工作，不按固定人数或“前端一个、后端一个”拆分。机器可用容量、上游限流、实际共享资源与用户明确预算/策略决定何时能执行；不足时保留完整任务图排队，Hub 分别显示期望并行规模、实际运行数和等待原因。恢复容量后从同一图继续，Karajan 不截断任务、不降低目标，也不把临时容量改写成业务拆分上限。不存在未经用户选择的默认最大 Agent/并发数量；无此数量限制不代表无限资源或消费许可。

运行图与部署预览分开：预览对应固定模板和调度授权，运行图对应该定义下已生效的具体任务修订。两者保留可追溯引用，图表/详情展示同一当前运行 revision。纯状态变化、队列唤醒和收据核对由事件与可信程序完成，不反复调用调度模型轮询。

### 准确确认与真实部署

保存草稿、登记模板、确认并部署、确认部署并运行是不同操作。确认摘要显示目标项目/槽位、bundle/file digest、模板 compiled digest、角色与来源、权限影响和是否立即运行。一次准确确认可以完成冻结、登记与部署，不要求用户先发布模板再重复批准同一部署；普通聊天文本或模型表示赞同不构成批准。

合法参数化模板可以在没有业务输入时仅部署。若用户明确选择同时运行，确认额外绑定本次 input digest、初始 Plan revision/run_plan digest、调度授权与执行授权；输入未确定时不能批准含糊的运行。初始计划可以包含获授权的动态调度步骤，不要求提前固定其尚未产生的子任务。模板编译摘要、初始实例摘要和后续运行图修订分别展示，不因更换输入或范围内扩图重写模板及原批准。

可信部署器先持久化命令，在受管数据根物化并校验 pending 包；调度器准备加载并读回同一文件/编译摘要，期间旧 active 仍是生效入口，pending 不接收新 Run。只有加载/就绪核验通过且 expected active revision 条件更新成功，才发布 active 并返回 ready 回执。准备失败保留旧 active；切换结果未知时先核对，不猜测哪一版生效。

ready 表示当时配置已加载并满足部署条件，不能承诺未来运行成功。资格缺失或加载失败显示 blocked/failed/unknown；未明确授权不自动付费探针。已有 Run 固定原定义与授权，范围内运行图可依调度命令产生新 revision；新 Run 使用明确选择的生效配置，仍执行当前资源与权限准入。“部署并运行”在原一次复合授权内顺序产生部署和 Run 回执，不重复确认，也不因请求重传多开 Run。

重新打开页面可查看真实 active 配置、文件、同源预览和回执，而非只看最后草稿。服务重启先重新加载/核对 active，历史 ready 回执不能替代新进程加载事实。回滚绑定具体历史版本与当前槽位 revision，经过同样 pending/读回/active 流程；它不撤销旧 Run、消费或远端产物。

### 快捷新建与模板复用

会话标题旁提供“＋新对话”，任务区提供“＋新任务”。新对话为空，旧会话、草稿、部署和任务仍可切回；新任务先保存目标，可交给 Designer/Commander 形成提案，也可实例化选定的已部署流程。保存或导航不隐含批准，不把新任务插入旧批准版本。

直接复用模板时，用户选择版本、提供符合契约的输入并查看初始步骤、调度授权和资源影响；无需重新创作，也不强制额外规划模型。更换定义或扩大运行授权时生成新提案并说明影响，用户批准后生效；获授权角色在原范围内扩展或调整运行图则自动校验提交新 revision，无须逐项再次批准。

### Tasks / Agents 与产物详情

Tasks 按自定义步骤与依赖组织，Agents 按模型 Attempt 展开；确定性检查、人工决定、汇合和部署各有其真实类型，不伪装成 Worker。看板可按角色、执行种类、模型、来源和状态筛选，只改变视图。并行任务分别显示 workspace、Attempt 和结果，汇合必须等待所选必需输入，不能以首个完成代表全部完成。

详情提供“返回 Commander Hub”，保留草稿、批准版本、选择和状态。报告直接显示产物与引用；patch/pr 显示候选及其基准。五类证据页签保持统一入口：

- **Diff**：选中配置或产物版本的差异；代码候选显示批准基准、文件、来源任务与冲突。
- **Checks**：该对象要求的检查、配置版本、运行事实和证据；进行中、未知、缺失与通过分别展示。
- **Review**：适用的审查输入、实际 Reviewer、verdict、问题和修复轮次；没有义务时明确不适用，有义务未完成时显示原因。
- **Logs**：按创作/部署命令、Run/Attempt 与时间查看事件、权限、路由、消费核对和错误；秘密不进入日志。
- **Dependencies**：步骤输入、条件、阻塞、汇合、返工范围和旧证据影响。

不适用与未完成必须区分。report 无 PR 不构成失败；pr 的缺失 checks 或独立 Review 不能被隐藏成不适用。详情动作绑定选中对象及其当前 revision，断线重连先快照后事件，过期操作返回原因。

### 同一会话的用量统计

“用量”面板默认展示当前项目、当前 Commander 会话从创建至今的全部已记录消费，包含 Commander、Designer、顾问、Worker、Reviewer 和自定义模型角色；未创建 Run/Task 的调用明确归入“会话对话/创作”或“无任务”，确定性步骤不伪造 token。可限定 Run、时间范围，并按以下维度分组、排序及组合筛选：

| 查看口径 | 用户可见内容 |
|---|---|
| 角色 / Agent | 各角色合计，展开到每个实际 Agent 执行实例及 Attempt；同角色多个实例不混淆 |
| 任务 | 每个任务及历次重试/改派消费；父任务自身与含子任务小计分开，已替代任务仍可查 |
| 模型 | 实际模型的合计和明细，可切换请求模型/别名；未知实际模型单列，不从别名补齐 |
| 底层 provider | 每个已验证实际 provider 的用量，展开实际模型、网关路径、脱敏账户或池及计费通道；同模型跨 provider 可对比 |

各组显示输入、输出、总 token 与调用数，支持时显示缓存读取/写入和推理明细及包含关系。已报告、估算、未知分开，部分缺失显示“已知小计＋待核对”，不能当完整实耗或零；预算预留和额度百分比不冒充已耗 token。缓存/推理子项不与已包含它们的输入/输出重复相加。只支持 Attempt 总量的来源显示该粒度，不伪造逐调用精度；实际 provider/model/account 的可见性分别标注。

点击分组可追溯任务、Agent、模型调用及可信路由/usage 回执。筛选后的分组、总计和明细使用同一账本快照；范围与最后更新时间始终可见，未知分组不被隐藏。失败、取消、重试及迟到用量继续计入原身份，重复回执不重复累计，配置或角色改名不改写历史归属。

任务与 Agent 卡片可进入对应筛选的用量详情，返回时保留会话草稿与选择。事件到达更新统计，断线恢复先读快照，旧会话结果不覆盖新会话；打开、筛选和刷新不调用模型。用户另行要求 Commander 分析用量时，其分析调用同样计入会话。账户外部消费只用于额度观察，不分摊进本会话。

### 实时反馈

Designer 和所有自定义模型角色使用一致图标、文字及最近反馈时间；确定性步骤显示自身执行状态。等待模型、依赖、人工决定、空闲、完成、失败和反馈中断可区分，不能只靠颜色或动画。

执行事实、模型反馈与浏览器连接新鲜度分别表达。可信运行心跳尚新鲜但无输出时显示等待响应；反馈过期或订阅断线时保留最后时间并显示待核对。连接心跳和网页计时器不证明模型正常或终态。恢复读取同一 Attempt，完成/失败仅来自可信结果事件，各视图不通过模型轮询状态。

## 路由、授权与改派

首次由所有者登记网关连接和必要默认配置，provider 登录及管理在外置 CLIProxyAPI 完成。模型目录可见、连接可达、所需能力合格和资源可准入分别展示；网关别名不证明实际来源。日常对话复用已授权集合，内部 JSON、规则和预算详情按需展开。

用户明确固定的角色、模型、来源和依赖进入批准约束；允许角色按任务选择的绑定集合与依赖调整范围同样明确记录。严格单一绑定不因资源短缺被静默替换或提价。已有明确 opt-in 的合格替代集合可在原范围内自动创建新 Attempt，保留原因、目标和消费；用户选定主 Commander 的交接仍由用户决定，其他调度角色的授权内创建/委派不重复要求主控交接批准。当前 Attempt 的模型、来源、工具范围和计量路径不热修改，替代前必须证实旧执行停止或隔离。

能力、隔离、计量和预算都是硬约束。额度 unknown 只有在已有有限保守授权内准入，超界则阻塞；未知不显示精确余额，现金 API/现金后备继续按现有授权边界暂停。自定义角色、Workflow 配置或网关路由都不能扩大消费权限。

## 状态与异常行为

| 状态 | 工作台表现与行为 |
|---|---|
| 空态/设计草稿 | 可开始设计或使用已部署模板；无 Run 仍保留会话，不伪造执行卡片 |
| 校验/待确认 | 图表与文件标明同一 revision；错误可定位，旧预览不可批准；语法通过不等于可执行 |
| 部署 pending | 展示物化、加载与读回事实；pending 不接收新 Run，旧 active 可读 |
| 部署 ready | active 已条件发布，展示加载回执和生效配置；不等于 Run 已启动或成功 |
| 运行中 | 按实际步骤显示角色/执行种类、固定绑定、进展和证据；暂停只阻止新派发/交付 |
| 调度扩图/容量排队 | 显示获授权角色的决策、已提交运行 revision、待执行任务与资源等待原因；范围内扩图不弹出新批准，容量不足不删除任务 |
| 阻塞/未知 | 具体原因、受影响对象与可行操作可见；不能绕过资格或把未知当作失败、完成或停止 |
| 恢复/回滚 | 先核对原命令、文件、pending/active、Attempt 和远端结果；不重复调用、激活、Run 或 PR |
| 产物完成 | 按 report/patch/pr 显示当前版本、必需证据与限制；PR 创建、CI、用户合并分别呈现 |

## 默认代码交付模板的验收场景

以下保留原工作台首演范围，用于验证 code-to-pr 模板的最小链路；两个任务是历史验收样本，不是默认数量或上限，不要求研究、文档或每个 Run 执行它：

1. 在仓库会话选择该模板与主 Commander 的合格 Profile，描述可拆成两个独立编码任务的小需求。
2. Commander 只读需求与仓库提出分工；用户修改角色、模型来源、依赖和检查/PR 权限，批准正在看的同一实例计划。
3. 两个 Worker 的独立 Attempt 真实并行，固定顺序组合为候选，再对该冻结候选运行必需 checks 和独立 Review。
4. 可信交付入口创建并核对同一 PR，Hub 汇总事实；修复或重派有界且产生新 Attempt，PR/CI/合并分别呈现。

该场景的历史 AC 与父 Issue 继续验收；新增报告或 patch 流程不会使其自动完成。
