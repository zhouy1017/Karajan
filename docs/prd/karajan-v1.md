# Karajan PRD v1：多来源 Agent 的流程设计、运行与交付

版本：1.7（工作台 r9）。依据：已确认的个人单机与受控执行基线、2026-09-14 的网关/Workflow/部署/角色调度决定，以及 2026-09-16 新增的同一 Commander 会话多维 token 用量与实际底层 provider 统计要求。状态：新增统计与完整链路待实现及验收，不以设计文件宣称已可用。

本文维护产品目标、FR01–29 和 PRD-AC01–06；[Commander 工作台设计](commander-workbench.md) 维护完整交互及 UX-AC01–27。技术承接见 [网关](../architecture/08-provider-gateway.md)、[角色/Workflow](../architecture/09-configurable-workflows.md)、[对话与部署](../architecture/10-conversational-workflow-deployment.md)、[角色主导调度](../architecture/11-role-directed-scheduling.md)、[会话用量](../architecture/12-conversation-usage-accounting.md) 和 ADR 0005–0009。原代码到 PR 范围保留为默认模板及其独立验收，不要求每种流程都生成 PR，也不因增加非 PR 流程而将旧 Issue 视为完成。

## 用户问题与产品目标

一个用户同时使用多种订阅与 API 模型，希望按工作需要定制职责、分配模型并组织协作。目前需求拆分、配置编写、上下文传递、额度管理、执行跟踪和成果汇集需要手工完成；流程设计与实际执行也容易脱节，难以判断当前生效的是哪份配置、哪些任务真的完成以及结果是否经过验证。

Karajan 让用户在单机 Web 工作台通过文字设计流程，使用同源图表审阅真实配置，确认后实际部署到引擎，并运行得到符合验收要求的报告、补丁或 PR。模型来源、职责、流程、权限与资源由用户掌握；平台给出可复核的生效版本、执行事实和产物证据。

## 产品方案

**设计与复用。** Hub 内的 Workflow Designer 接收自然语言、编写声明式 WorkflowBundle，可信服务保存并编译，生成同一版本的流程图、角色/步骤表与 diff。文字、表格或文件修改均产生新 revision。创作会话可先于目标 Workflow/Run 存在，模型调用和自动纠错具有持续累计的预算与次数边界。用户也可直接选用已部署模板并填写本次输入，无需再次设计或强制调用规划模型。

**确认与部署。** 用户确认具体文件/bundle 摘要、模板编译摘要、目标与权限后，可信部署器物化 pending 配置，调度器加载读回，再条件发布 active 并返回 ready 回执。模板可在无业务输入时仅部署；明确“部署并运行”时，一次确认另绑定具体 input、初始实例 Plan 摘要、调度授权与执行授权。初始计划可包含动态调度步骤，不要求预先列尽后续子任务。模板登记、文件导出或模型说“完成”不等于部署成功；部署、运行与产物验收分别呈现。

**运行与交付。** 自定义角色定义职责、输入输出、工具约束和完成标准，Workflow 定义步骤、依赖、条件、并行汇合、人工节点、有限返工及可授予的调度范围。获授权的 Commander 或自定义调度角色按实际任务决定拆分、绑定、依赖和派发规模；可信协调器校验其命令，自动提交范围内运行图修订并做资源准入、执行和状态提交。只有扩大原授权才要求新确认，不逐子任务重复审批。report、patch、pr 按各自目标完成；PR 必须保留同候选的机器检查、独立审查、有效授权及独立远端交付门。

**自适应规模。** Karajan 不硬编码前后端分工，不内置 Agent、角色、任务数或并发人数上限。调度角色决定业务拆分，机器与上游实际容量、共享资源和用户明确预算/策略决定可运行时机；暂时不足就保留完整任务图排队，不截断任务或把当前容量变成业务拆分上限。定义和原授权冻结，运行图的每次变化有版本，已启动 Attempt 的绑定不变。纯状态更新、队列唤醒和核对不消耗模型轮询。

**模型接入。** 多来源模型默认通过外置 CLIProxyAPI；provider 登录、凭据刷新与协议转换在网关完成。Karajan 保留模型绑定、受控调用、原生资源账本及 runtime 工具执行。严格单一来源不被网关或程序静默替换；只有事先批准的合格替代集合才可用于新的 Attempt。当前 Attempt 不热切换模型、来源或工具权限。

**会话用量。** 同一 Commander 会话内查看全部 Run 及对话/创作调用的 token 消耗，按角色、Agent 实例、任务、模型和实际底层 provider 分组及交叉筛选，展开到可信调用记录。请求别名与实际路由分开，已报告/估算/未知分开，失败/重试/取消消费保留；统计刷新无需模型调用。

代码交付内置模板保留 Commander 理解需求、两个 Worker 并行、固定顺序组合候选、checks、独立 Review、同一 PR 的历史最小首演场景；两任务不是产品默认数量或上限。角色名称和该拓扑可被其他定义替代，但用户授权、可信准入、资源硬约束和 PR gate 不能被重命名或配置绕过。同一 Run 可明确授权多个角色管理不同范围，用户选定主 Commander 的有效任期仍唯一；子图角色可在明确委派规则内取得权限子集，顾问或 Designer 不因名称获得调度权或第二份批准权。

## 目标与成功条件

| 编号 | v1 成功条件 |
|---|---|
| G1 | 默认 code-to-pr 模板在已有仓库完成可拆为 2–3 子任务的小功能，用户批准后获得同一需求的 PR；原出口继续独立验收 |
| G2 | 同一 Run 可使用多个来源的合格模型，每个 Attempt 可追溯任务、角色定义、Profile、规则、资源与结果 |
| G3 | Rulebook 控制资格和换源，资源短缺不降低原要求、不借用未批准现金，也不因角色改名扩大权限 |
| G4 | 外部消费、失联、取消、旧结果、部署/交付应答丢失都有正确停止、核对和继续路径 |
| G5 | 用户可在 Hub 理解配置、生效版本、计划、步骤、阻塞、产物、证据、费用及适用的 PR/CI 状态 |
| G6 | 经外置 CLIProxyAPI 的统一连接访问不同已验收 provider，模型别名、实际来源与共享资源不会混淆 |
| G7 | 无需修改产品代码即可创建非内置角色并运行不同 Workflow，report/patch/pr 分别按批准目标完成 |
| G8 | 用户以文字和图表创作、修改并确认真实配置；获批包经 pending 加载读回后 active，实际 Run 读取该配置执行 |
| G9 | 获授权角色按任务实际扩展运行图并派发，范围内自动生效；任务规模不被内置人数上限或前后端模板截断，实际资源不足可排队恢复 |
| G10 | 同一 Commander 会话可按每个角色/Agent、任务、模型和实际 provider 查看 token 消耗，分组与总计同源可核对，路由及用量缺口明确 |

真实任务记录成功率、修复次数、耗时与消费；不承诺模型对所有需求都成功。正确展示失败、未实现和阻塞也是验收的一部分，不能通过降低目标制造完成。

## 用户与使用边界

唯一用户是平台所有者，运行于个人单机 Web 工作台，接受 Windows＋WSL2，必要时使用容器。项目以受管仓库为工作上下文，支持代码开发及相关研究、文档和报告；report 可只读材料并写入获准产物区，patch 提供确定版本的补丁，pr 才进行获准的远端交付。默认不直接修改用户原工作区。

来源目标仍包含 ChatGPT 订阅、Claude 订阅、DeepSeek 官方 API、OpenCode Go 订阅与第三方 API。各来源按固定网关版本、模型/账户映射、runtime 能力和真实证据单独启用，不能假设 CLIProxyAPI 已使所有来源合格。需要原生专属能力时使用显式选择的兼容 Profile，不能静默回退。厂商、型号、额度和金额未配置就如实显示，不代表无限可用。

“部署 Workflow”仅指将配置加载并激活于 Karajan 引擎，不包括部署网关、网站或外部服务，不默认创建定时触发和无限运行许可。部署 ready 证明当时已加载及能力条件成立，实际 Run 仍按当前授权、资格和资源准入；未获授权的 readiness 检查不自动发起付费探针。

5. 作为需求提出者，我希望创作与规划使用既有预算，自动修复、重试和重启都不清零累计消费。
6. 作为需求提出者，我希望主 Commander 可征求顾问意见，同时保留单一有效提案任期。
7. 作为需求提出者，我希望未决问题得到明确处理，使各自定义角色收到可执行的任务简报。
8. 作为平台所有者，我希望批准准确的配置/计划版本、来源集合、权限与动作范围。

19. 作为平台所有者，我希望按自定义依赖在独立工作区并行，并在汇合时等待全部必需输入。

22. 作为平台所有者，我希望复杂/关键代码使用适用的不同模型家族审查，缺资格时正确等待。

36. 作为平台所有者，我希望留在同一个 Commander 对话中，查看每个角色 Agent、每个任务和每个模型消耗的 token，并组合筛选及展开明细。
37. 作为平台所有者，我希望看到实际底层路由 provider 及对应用量，区分请求别名、真实模型和可信程度，失败或重试也不漏账。

## 功能需求与验收

FR01–20 保留原需求责任，涉及代码、主 Commander 或 PR 的条款按相应目标/模板适用；FR21–25 承接网关、自定义流程和 r7 设计部署，FR26/27 承接 r8 授权角色调度与自适应规模，FR28/29 承接 r9 会话用量与实际 provider 归属。原数量样本仍用于原场景验收，不定义产品数量上限。Axx 指原架构验收，新增行为必须补充自己的证据，不能声称旧 Axx 已自动覆盖。

| ID | 必须实现的行为 | 可观察验收及关联 |
|---|---|---|
| FR01 项目与输入 | 登记项目/仓库身份、适用基准与目标分支、输入和验收；不默认修改原工作区 | 合法输入关联固定对象；未知/越界仓库拒绝执行。PRD-AC01，A01、A16 |
| FR02 接入与能力 | 来源经统一网关/显式兼容 Profile 登记，只有角色所需能力通过的配置可执行 | 模型可见不等于启用，参数被忽略或认证/能力未知不能冒充合格。A02、A12、A13，FR21 |

## 核心用户流程

1. 打开项目 Hub。首次设置只补齐必要连接/默认配置，日常复用；选择“设计流程”或“使用已部署流程”。
2. 设计时向 Designer 描述职责、依赖和产物目标，获得真实配置包及同源图表/diff，通过文字或字段迭代。复用时直接选择生效模板并提供本次输入，不强制模型调用。
3. 查看准确版本、来源、权限与资源影响。可以只确认部署参数化模板，也可在输入/初始实例计划与调度范围确定后一次确认部署并运行；已部署模板的运行确认绑定其具体实例及授权。
4. 需要部署时，可信服务持久化 intent、物化 pending，调度器加载读回后条件发布 active，Hub 显示 ready 或具体失败/未知。仅部署不启动流程。
5. 配置动态调度的流程由获授权角色按实际任务提交拆分和派发；可信协调器自动校验范围内命令、记录运行图修订并按当前资源准入执行。固定或确定性流程可直接按批准指令推进，不强制增加调度模型调用。依赖、并行、人工节点和有限返工及每个 Attempt 均可追溯；容量不足时完整排队，超授权才等待新确认。
6. 在同一 Hub 查看 report/patch/pr 及其必需证据。PR 另经独立交付入口，CI 与合并分别呈现；不需要 PR 的流程按自己的完成条件结束。
7. 运行中或结束后，在同一会话展开用量，按角色/Agent、任务、模型及实际 provider 查看总量、交叉分组和调用明细；用量缺失、估算和迟到核对状态直接可见。

### 关键异常

| 情况 | 用户看见的结果与动作 |
|---|---|
| 配置校验失败或创作修复上限到达 | 定位文件/步骤，保留当前配置与诊断；有界修复停止，不自动部署 |
| 参数化模板尚无业务输入 | 可仅部署合法模板；具体 Run 在输入与实例计划确定后批准 |
| pending 加载失败或 active 切换结果未知 | 前者保留旧 active；后者查询实际提交和加载事实，不宣称部署成功 |
| 配额耗尽且存在已批准合格替代 | 适用任务在原边界内创建新 Attempt，展示原因；严格单一绑定保持阻塞 |
| 必需审查无合格角色或预算不足 | 等待有效配置/预算，不删除证据门或把不适用当通过 |
| 主 Commander 不可用 | 展示交接方案，由用户决定，不提前启动替任 |
| 执行是否停止未知 | 保留占用并核对，不偷偷再开 writer 或重复发送模型请求 |
| 修复/重试达到边界 | 保存产物和问题，停止自动循环，等待有效决定 |
| 调度角色在范围内扩图/派发 | 自动校验并提交新的运行图 revision，显示决策与影响，不逐子任务再次确认 |
| 调度命令越权或任期/图版本过期 | 越权展示所需新授权，过期拒绝；不因角色名称或重试取得权限 |
| 业务拆分大于当前机器/上游容量 | 完整任务图保留并排队，容量恢复后继续；不内置人数上限或改写业务目标 |
| 部署、启动或 push/PR 应答丢失 | 查询同一命令/对象恢复，不重复激活、Run 或交付 |
| 旧备份恢复 | 先冻结并核对版本、消费与远端事实，由用户决定继续范围 |

## 已确认的实现决定

- 用户授予调度与执行权限，获授权角色拥有范围内业务拆分、分配和派发决策；Karajan 负责校验命令与唯一可信状态提交、准入、Run/Task/Attempt 及交付事实。
- 同一 Run 可以有多个有效授权调度角色；重叠任务图修改按明确归属与 CAS 校验，不允许后返回的模型结果覆盖已接受决定。主 Commander 的单一有效任期不构成全局调度角色独占。
- WorkflowBundle 是真实版本化文件与依赖清单；WorkflowPreview 是其编译投影，WorkflowDeployment 记录物化、读回与条件激活。
- 模板 bundle/compiled digest、每个 Run 的 input/初始 run_plan digest 与后续 TaskGraphRevision 分开固定；SchedulerGrant 和原定义不被扩图改写，每次 SchedulingDecision 可关联其实际图修订。
- RoleDefinition/WorkflowDefinition 可定制，执行种类由受信任实现注册；角色名称、自由脚本或提示词不构成权限。
- 外置 CLIProxyAPI 拥有 provider 凭据/协议；Karajan 调用层负责有界准入与账本，受控 runtime 执行工具，独立交付入口持有远端权限。
- 单机模块化 Python/FastAPI、React/TypeScript 和 SQLite；模型/检查/交付在各自受限执行域运行。
- 本地预留与服务报告分开，当前共享账户保护策略、Run 固定授权和原币预算共同约束。
- 产物与候选不可变，证据绑定内容、输入和环境；无内置 Agent/任务/并发人数上限，按实际机器/上游容量及用户明确政策排队执行。代码模板的 2 轮质量修复、每根任务 2 次基础设施重试作为既有有界返工规则保留，沿稳定身份累计，不因新增任务清零。
- 动态 ExpansionSet 明确封口后才判断汇合完整；既有必需任务、产物和 PR gate 不因删图或重新拆分消失。调度决策模型调用受原预算约束，队列状态和事实核对不调用模型轮询。

具体字段与迁移以活动架构契约为准；本节记录决定，不声称代码已经实现。Bernstein 和旧原生适配器只可在同一受控边界、对应资格成立时复用。

## 测试与非功能要求

通过最高可观察接口验证：文字/模板输入→真实配置与同源预览→准确批准→pending/读回/active→实际 Run 读取配置→角色调度命令与版本化运行图→产物/证据。至少验证两种不同的可执行流程；不能在测试中另写固定图来冒充配置驱动。r8 另以适合 1、3、7 项工作的输入验证实际拆分、范围内自动生效、越权拒绝、动态扩展封口、容量降低/恢复和重试幂等。样本数量不成为产品上限。PR 模板另核对机器 checks、独立 Review、同候选和远端对象。

C/U 验证产品/界面行为，P 验证本机物化、执行、隔离与恢复，S 验证实际 Designer/执行角色及来源资格，G 验证远端交付。fixture 只证明其覆盖层级；旧通道实测不能继承为网关资格，旧候选通过不能升级新版本。真实探针受既有授权，failed/unsupported 的调查结果不意味着该能力可启用。

持久命令、重复事件、重启与历史备份恢复保持同一业务含义；未知不改写成成功、零消费或恢复余额。所有业务 API、事件和产物读取认证，秘密不进入配置、普通日志和导出。普通本地命令/快照 p95 目标小于 1 秒，持久事件正常 2 秒内到 UI，排除模型、外部网络与检查耗时。记录创作/运行成功率、修复、等待、交付时间、已知消费及未知比例。

## 首版之外

自动 merge、多用户/多租户、多机队列、通用插件市场、自动学习并发布路由规则、通用拖拽画布、大范围底座 fork，以及 Karajan 内自行提取/转换订阅 token。对话创作、真实文件、同源流程图/表格、外置网关接入与真实 Workflow 部署属于本版范围；字段/API 编辑是支撑能力。外部网站/服务部署与自动定时触发不是本次配置部署的隐含功能。

不要求所有来源具有相同能力或精确额度接口；未知必须有可观察的产品行为，未合格来源保持明确未完成记录。

## 原范围承接与实现状态

M0–M4 是历史需求责任索引，不是当前排期或运行时状态机。其原出口保持如下，原 2–3 任务等样本不构成 r8 的人数/任务上限；实际队列以 [当前业务顺序](../planning/business-first.md) 和远端 Issue 为准，r6–r9 新范围按 [治理索引](../planning/design-governance-20260909.md) 另行承接。

| M1 | Web 输入/规划/批准到跨来源串行代码实现、验证与 PR；固定规则、预算、有限 unknown 准入和最小人工 Commander 交接 |
| M2 | 2–3 子任务并行、组合验证，并逐项接通其余来源 |
