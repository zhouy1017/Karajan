# Karajan PRD v1：多来源 Agent 从需求到 PR

版本：1.1。依据：2026-09-05 已确认的设计基线 D01–D09。状态：产品范围与行为已确定，进入实现。此次修订更新执行授权与任务拆分状态，产品行为不变；实际能力仍须逐项验证。

## Problem Statement｜用户问题

我同时使用多个订阅与 API 模型，希望把高级模型的设计能力和较低成本模型的执行能力用于同一个代码项目。目前我需要手动选择执行者、转移上下文、管理额度、汇集代码与检查结果，很难同时知道任务是否可靠完成、是否换了来源，以及还剩多少资源。

Karajan 的目标是让一个用户在单机 Web 工作台提交需求并确认计划，随后自动获得经过检查和独立审查的 PR；模型来源、路由规则和资源分配仍由用户掌握。

## Solution｜产品方案

每次 Run 由一个主 Commander 理解意图、组织设计和汇总顾问意见。平台将计划转换成明确任务，按用户 Rulebook 选择满足角色、复杂度、风险和工具要求的 Execution Profile，并根据订阅/API 配额及预算决定何时执行。不同来源可以在同一项目担任不同角色。

Worker 产出确定版本的候选，平台集成、验证，再交给独立 Reviewer。必要修复在有界次数和预算内进行；通过后由独立交付入口创建 PR，合并由用户决定。异常、未知消费和人工决定有明确状态，不能以“Agent 已结束”代替验收通过。

## 目标与成功条件

| 编号 | v1 成功条件 |
|---|---|
| G1 | 在已有仓库完成一个验收明确、可拆成 2–3 子任务的小功能，用户确认计划后获得同一需求的 PR |
| G2 | 同一 Run 能使用多个来源的模型；每次 Attempt 可追溯任务、角色、Profile、规则、资源与结果 |
| G3 | Rulebook 控制资格和换源，资源短缺不能降低原要求或借用未批准现金 |
| G4 | 配额被外部消费、执行失联、取消、旧结果和交付应答丢失都有正确停止/核对/继续路径 |
| G5 | 用户能在 Web 理解计划、当前进度、阻塞、路由理由、候选、证据、费用及 PR 状态 |

通过率、修复次数、时间与实际费用作为真实任务基线记录；不承诺模型对所有需求都成功。正确表达失败和阻塞也是产品验收的一部分。

## 用户与使用边界

唯一用户是平台所有者，部署在一台个人机器，接受 Windows＋WSL2，必要时使用容器。首版面向已有仓库的代码开发；首个真实仓库、分支、小功能与检查命令在 M0/真实验收准备时填入。

接入目标包含 ChatGPT 订阅、Claude 订阅、DeepSeek 官方 API、OpenCode Go 订阅与第三方 API。M0 首先验证一个订阅端和一个 API 端；这不删除其他来源的 v1 接入目标。厂商、型号、具体额度和金额是接入参数，未填写表示未配置，不表示无限可用。

## User Stories｜用户故事

1. 作为平台所有者，我希望登记已有仓库和允许目标分支，以便任务有明确的代码基准。
2. 作为平台所有者，我希望分别登记订阅和 API 通道，以便同名模型的身份、费用与额度不会混淆。
3. 作为平台所有者，我希望看到执行器的已验证、未验证与不支持能力，以便选择适合角色的配置。
4. 作为需求提出者，我希望描述目标、约束和验收标准，以便 Commander 先理解我要的行为。
5. 作为需求提出者，我希望在规划开始前设置规划预算，以便讨论与顾问调用也有资源边界。
6. 作为需求提出者，我希望主 Commander 可以征求其他高级模型意见，以便重要取舍得到复核。
7. 作为需求提出者，我希望未决问题先被澄清，以便 Worker 收到的是可执行简报。
8. 作为平台所有者，我希望确认具体版本的计划、来源集合和权限，以便后续执行遵循已确认范围。
9. 作为平台所有者，我希望修改计划时看见影响，以便保留有效成果并重做受影响工作。
10. 作为平台所有者，我希望按角色、复杂度、风险和能力配置矩阵，以便不同任务使用合适模型。
11. 作为平台所有者，我希望无付费调用地模拟规则，以便看清候选、排除原因和选择顺序。
12. 作为平台所有者，我希望主 Commander 来源不限制 Worker/Reviewer 来源，以便跨服务组织协作。
13. 作为平台所有者，我希望平台保护主 Commander 余量，再平衡资源、费用和速度，以便保留必要设计能力。
14. 作为平台所有者，我希望短周月窗口与账户共享池共同生效，以便并发任务不重复分配本地额度。
15. 作为平台所有者，我希望看见已报告、估算和未知用量，以便不依据虚假精确余额作决定。
16. 作为平台所有者，我希望现金按原币预算限制，以便失败、重试和跨渠道计费不绕过上限。
17. 作为平台所有者，我希望 Worker/Reviewer 在已批准合格集合内自动换源，以便资源故障不用每次干预。
18. 作为平台所有者，我希望主 Commander 换人时先看到交接方案并亲自决定，以便保留负责人选择权。
19. 作为平台所有者，我希望依赖满足的任务在独立工作区并行，以便加快完成而不互相覆盖代码。
20. 作为平台所有者，我希望候选冻结后再验证，以便检查结果对应实际交付内容。
21. 作为平台所有者，我希望每个 PR 有独立 Reviewer，以便作者不能自行宣布审查通过。
22. 作为平台所有者，我希望复杂或关键变更使用不同模型家族审查，以便缺少合格审查者时正确等待。
23. 作为平台所有者，我希望修复次数有累计上限，以便新建任务或换源不会导致无休止循环。
24. 作为平台所有者，我希望暂停派发与取消执行含义明确，以便知道已有进程是否仍在运行。
25. 作为平台所有者，我希望重新打开页面或正常重启后恢复同一 Run，以便无需手工重建状态。
26. 作为平台所有者，我希望历史备份恢复后先核对再决定继续，以便旧授权和旧预算不被意外重新激活。
27. 作为平台所有者，我希望得到唯一且可更新的 PR，以便网络超时不产生重复交付或覆盖他人修改。
28. 作为平台所有者，我希望分别看到 PR 创建、远端 CI 和合并状态，以便自行作最终合并决定。

下列 FR 是产品需求；Axx 对应架构验收矩阵。新增的 PRD-AC 是此前矩阵未完整表达的产品动作，不能假称已被其他测试覆盖。

|---|---|---|
| FR01 项目与输入 | 登记仓库身份、基准、目标分支、验收要求；默认不修改用户原工作区 | 相同输入能关联同一基准；未知/越界仓库不执行。PRD-AC01，A01、A16 |
| FR02 接入与能力 | 五类来源按 Profile 分别登记，只有所需能力通过的配置可执行 | 未设置模型、认证/能力未知、必需参数被忽略时不能假称已启用。A02、A12、A13 |
| FR03 规划与顾问 | 预设规划预算；一个主 Commander 汇总；T0 未决事项留在规划 | 未确认实现前不写仓库；顾问不能成为第二个有权提交计划者。PRD-AC02 |
| FR04 计划确认 | 显示并绑定计划版本、任务图、范围、允许来源/升级集合、预算语义、检查和 PR 权限 | 批准旧版本被拒绝，普通范围内执行不用重复确认。A11 |

| FR06 Rulebook | 先执行硬资格约束，再按固定策略排序，提供无副作用模拟与原因 | T0 不派实现，T3 不因耗尽降级，歧义/缺规则阻塞。PRD-AC03，A08、A11 |
| FR07 跨来源派发 | 同项目每 Attempt 独立固定 Profile，内部模型/收费路径不静默改变 | Commander、Worker、Reviewer 可来自不同来源，变化记录来源和证据。A02、A12 |
| FR08 资源保护与准入 | 共享池当前 CapacityPolicy 对全部 Run 生效；原子登记全部适用约束 | 并发不半预留/双分配；Worker/顾问不能借主 Commander 保护量。A03、A04、A25 |
| FR09 配额观察 | 分开显示服务额度、平台预算、在途/待核对消费及置信状态；未知订阅额度仅在已配置且获准的有限保守模式下准入 | 并发、时长等必要限制缺失时阻塞；unknown 不作为零消费或无限容量。外部消费、延迟/重复报告和窗口重置不显示虚假精确值。沿用有效配置授权，不逐次询问。A05、A06 |
| FR10 现金限制 | 原币预算，默认可约束上限；价格失效/隐藏现金路径不自动消费 | 父子切片不双算，发送未知不归零；订阅不透明部分按 Attempt 报告。A18、A19、A26 |
| FR11 自动换源 | Worker/Reviewer 在预先批准且合格集合内自动换源，保留目标/风险/消费 | 旧执行已停止或实际隔离后新建 Attempt；无合格配置等待。A07、A08、A10 |
| FR12 Commander 交接 | 准备检查点、候选与费用影响，每次换人由用户决定 | 未决定前不启动替任；答复旧 term/提案不能换人；不依赖新决定的已批任务继续。PRD-AC04 |
| FR13 并行与候选 | 依赖驱动、每项目默认 2 writer、独立写区、固定顺序集成 | 任务结果能组合成确定候选；越界和冲突不静默被接受。A01、A13、A16 |
| FR14 质量与修复 | 每 PR 必需检查和独立 Review；T3 不同家族；每 Run 默认最多 2 轮修复 | 无合格 Reviewer、结果不确定或旧候选证据都不通过；同批失败只计一轮。A15、A16、A24 |
| FR15 生命周期 | 暂停停止新派发/交付；取消请求实际停止；未知先核对 | 不因 idle/超时判断成功或停止；旧结果不能交付、旧消费仍记录。A09、A10 |
| FR16 权限请求 | 原生工具权限按有效请求和当前授权处理 | 原范围可自动裁决，扩权需新授权；取消后的迟到批准无效。A23 |
| FR17 运行视图 | 展示任务、Attempt、路由原因、阻塞、候选、证据与资源 | 页面重连先快照再事件；无依据不显示精确进度/剩余任务数。A20、PRD-AC05 |
| FR18 恢复与维护 | 正常重启核对后按有效授权继续；旧备份冻结后由用户决定 | 业务终态但进程/消费未结束仍被核对；恢复不重放旧 outbox。A09、A21 |
| FR19 独立交付 | 仅交付入口有远端写入权，每步重新校验；同 Run 更新同一 PR | 超时先查真实结果，分支条件更新，无重复 PR、不覆盖外部 head。A14、A17 |
| FR20 完成与合并 | 必需检查/Review 通过并确认 PR 创建即默认完成，CI 单列，用户合并 | PR 创建不表示 CI/合并成功；若项目预设 CI gate，则按该额外条件完成。A01、PRD-AC06 |

以下验收条件明确前提、用户动作与可观察结果，随对应功能票据执行。M1 须覆盖项目输入、规划/顾问权限、最小人工交接、运行视图和完成语义；M3 完成规则模拟与交接工作台等完整产品体验。M0 不负责建设这些完整 Web 流程。

| ID | 前提（Given） | 动作（When） | 可观察结果（Then） |
|---|---|---|---|
| PRD-AC01 项目输入 | 已配置允许的仓库、目标分支及可解析基准 | 提交有效项目输入，再分别提交越界仓库路径或无法解析的基准 | 有效输入记录明确仓库身份与基准；无效输入返回具体错误，不启动模型或修改仓库 |
| PRD-AC02 规划与顾问 | 已配置规划预算和主 Commander，实现计划尚未确认 | 发起规划并在预算内征求顾问意见，顾问返回计划建议 | 主 Commander 汇总意见，顾问不能成为第二个有效计划提交者；调用计入规划预算，确认实施前不写仓库代码 |
| PRD-AC03 规则模拟 | 任务、Rulebook、授权及资源快照固定 | 对同一快照重复模拟规则 | 候选、顺序及排除原因相同；不启动模型、不产生预留或模型费用；歧义或缺规则返回明确原因 |
| PRD-AC04 人工 Commander 交接 | 当前 term 和交接提案有效，提案列明检查点、指定候选与资源影响 | 分别不答复、拒绝、确认当前提案，以及提交旧 term 或失效提案的迟到确认 | 未答复或拒绝时不启动替任；有效确认经检查点核对后，仅指定新 term 能提交有效决策；迟到确认被拒绝，不依赖新决定的已批任务可继续 |
| PRD-AC05 运行视图 | Run 有已持久化的任务、资源状态及可处理阻塞 | 刷新页面或断线重连，查看并尝试处理阻塞；另提交一个已过期动作 | 页面通过快照和后续事件显示一致状态及当前有效动作；过期动作被拒绝，不修改 Run；未知状态不显示为精确进度或剩余任务数 |
| PRD-AC06 完成语义 | 必需检查与独立 Review 已通过、PR 创建已确认，但远端 CI 尚未通过 | 分别查看使用默认完成条件、以及预先要求 CI gate 的 Run | 默认 Run 完成且 CI 状态单列；预设 CI gate 的 Run 继续等待该条件；两者均不自动合并，PR 创建不显示为 CI 或合并成功 |

## 核心用户流程

1. 设置项目、可用 Profile、规划预算与资源规则；未配置项明确显示。
2. 提交需求，与主 Commander 澄清；按预算征求顾问意见。
3. 查看并确认具体计划、验收、允许来源与费用范围。
4. 自动派发、并行实现、集成、测试和 Review；范围内有界修复与 Worker/Reviewer 换源自动进行。
5. 需要新范围、预算、权限或主 Commander 交接时显示具体方案；已有独立任务可继续。
6. 得到证据对应的 PR，查看远端 CI，自行合并。

### 关键异常

| 情况 | 用户看见的结果与动作 |
|---|---|
| 配额耗尽但有合格替代者 | Worker/Reviewer 自动换源，展示原因和新 Attempt |
| 无合格 Reviewer 或硬预算不允许 | 等待/更改配置或预算；不降低验收标准 |
| 主 Commander 不可用 | 交接方案待用户决定；不提前启动替任模型 |
| 执行是否停止未知 | 核对中，保留相关占用；不偷偷再开一个 writer |
| 测试/审查失败且达到修复上限 | 保存候选与问题，停止自动修复，用户决定下一步 |
| push/PR 应答丢失 | 查询同一远端对象后恢复；不盲目重复交付 |
| 旧备份恢复 | 先展示当前核对状态，再由用户决定继续哪些 Run |

## Implementation Decisions｜已确认的实现决定

- Karajan 是唯一业务协调器；执行器只报告其物理执行事实，Bernstein 通过接口验收后才可能复用。
- 使用版本化 Plan、Task Brief、Execution Profile、Rulebook、授权和候选；模型提出要求，可信程序计算实际权限与路由。
- Commander、Worker、Reviewer 是角色；订阅通道通过官方执行端接入，API 通道经有界推理 broker。
- 单机模块化 Python/FastAPI 后端、React/TypeScript 前端和 SQLite；执行与交付使用独立进程/权限域。
- 本地预留与服务报告分别核对；共享账户当前保护策略、Run 固定规则和原币预算共同约束。
- 候选不可变，证据绑定内容与基准；交付副作用具备明确身份、条件更新和未知结果核对。
- 默认 2 writer、每 Run 2 轮质量修复、每根任务 2 次基础设施重试，均可配置并累计计费。

具体接口与状态字段属于已确认技术设计及 M0 后收敛的接口规格；PRD 定义用户可观察行为，不重复底座实现。

## Testing Decisions｜测试策略

通过最高可观察接口测试行为：任务输入→派发/拒绝→执行事实→候选/证据→交付结果。针对规则/预算验证同一输入得到可解释决定，针对执行验证物理状态，针对交付验证实际远端对象。测试不能只断言内部方法被调用。

M0 建立有界探针、假 provider/进程和本地 Git remote，用可重复输入覆盖崩溃与计量空窗；真实订阅/API 测试单独记录版本、账户形态、计费边界和能力证据。自动测试随实现逐步加入 GitHub Workflow；实际完成情况以当前提交的检查和需求证据为准。

M0 是接口资格验证，不要求先造完整 Web/DAG 平台。假环境通过只证明协议行为；实际 Profile 只有在对应真实环境通过后才能标记合格。failed/unsupported 的完整探针可关闭其研究工作，但不代表该能力通过，也不能放行要求该能力的阶段。

## Non-functional Requirements｜非功能要求

- 持久状态、重复事件、重启与恢复保持同一业务含义，不能把未知重写为成功或余额恢复。
- 工具访问范围、认证/计费路径与交付凭据按具体执行环境验收；本地业务接口和事件/产物读取均认证。
- 配额观察、路由与用户动作有来源和时间；不保存实际密钥到规则、Issue、日志或运行导出。
- 本地普通命令/快照 p95 目标小于 1 秒，正常持久事件 2 秒内送达 UI；排除模型、外部网络和检查执行时间。
- 记录任务成功率、修复、交付时间、等待、已知消费与未知比例；以验收后的交付表现评估模型组合。

## Out of Scope｜首版之外

自动 merge、多用户/多租户、多机队列、通用插件市场、自动学习并发布路由规则、可视化工作流编程、大范围底座 fork，以及将订阅登录转换为通用推理 API。

不要求所有来源具有相同能力或精确配额接口；未知必须有产品行为。M0 完成不等于 v1 完成，部分来源尚不合格时保留明确未完成记录。

## 交付阶段与完成定义

| 阶段 | 当前规划粒度 | 阶段出口 |
|---|---|---|
